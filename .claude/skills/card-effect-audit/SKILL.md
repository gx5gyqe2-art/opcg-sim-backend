# カード効果監査（card-effect-audit）

カード DB の丸ごと差し替え後や既存カードの点検で、**各カードの効果が本文どおり、抜け漏れなく
発動するか**を確かめる手順。機械の部分は `tests/scripts/card_effect_audit.py`（`make card-audit`）、
判断の部分（意味のレビュー）は Claude が行う。結果は確認済み台帳に残し、次回は未確認・変化した
カードだけを見る。

## 前提

- Rust の wheel が入っていること（`make rust-develop`）。無いと scan が止まる。
- 作業はブランチで行い、CLAUDE.md の開発リズム（`make test` green → push → PR・マージは指示待ち）に従う。
- 機械の検査は**優先度づけと見落とし防止の網**であって、正しさの証明ではない。
  「指摘なし」でも意味のレビューは省略しない。

## 手順

### 1. scan（機械の検査）

```bash
make card-audit                              # 台帳で未確認／本文変更／実装変更のカードだけ
make card-audit CARD_AUDIT_ARGS=--all        # 全走査（既存カードの点検）
make card-audit CARD_AUDIT_ARGS="--set OP15" # 品番の接頭辞で絞る
make card-audit CARD_AUDIT_ARGS="--cards OP01-016,OP09-081"
```

出力は `/tmp/card_effect_audit/`（`report.json`・`summary.md`・`effects.json`）。全 2,800 枚で約 10 秒。
`summary.md` の冒頭に **git HEAD の DB との差分（追加・本文変更・削除）**が出る。差し替え直後は
ここで新カードを把握する（比較元は `CARD_AUDIT_ARGS="--base <ref>"` で変えられる）。

**`LOAD_FAIL` が出たら最優先**: パーサが Rust の知らない効果種別（ActionType／ConditionType／
TriggerType）を出している＝**エンジン未実装**。この状態では実行検査が回らない。該当カードと
未知の名前を報告し、エンジン側の実装を先に行う（ユーザに確認してから）。

### 2. 指摘の読み方

| 重さ | 指摘 | 意味 | まず疑うこと |
|---|---|---|---|
| E | `LOAD_FAIL` | 効果 JSON を Rust が読めない | エンジン未実装の効果種別 |
| E | `PARSE_OTHER` | 未実装句（実行時に何もしない） | パーサのルール不足 |
| E | `NO_ABILITY` | 本文があるのに能力が 0 | パーサが本文全体を読み飛ばした |
| E | `UNKNOWN_TAG` | 見たことのない【】見出し | **新しい仕組み**（パーサ・エンジン両方に追加が要る） |
| E | `KEYWORD_MISSING` | 【ブロック不可】等がキーワードにも付与効果にも無い | キーワードの処理が無い |
| E | `PROBE_ERROR` | 発動・解決中にエンジンが例外 | エンジンの欠陥（プローブの盤面起因のこともある） |
| E | `ORACLE` | ターン1回／〜まで の取りこぼし | パーサ |
| W | `QUALIFIER_GAP` | 本文の限定語（元々の・上か下・できる・以外・色・好きな順番・否定条件・表向き・期間・すべて）に対応する欄が解析結果に無い | 限定語の脱落（pilot の ng の最多類型）。**レビューでは 1 件ずつ決着させる**（別の欄・エンジンの raw_text 読みで表現済みなら根拠を note に） |
| W | `UNCOVERED_TEXT` | 本文の句が解析結果のどこにも無い | **句の脱落**（複合句・「その後」・区切り無しの見出し） |
| W | `ACTION_NOT_FIRED` | 解析結果のアクションがどの経路でも実行されない | 実行系の欠落、またはプローブ盤面の限界 |
| W | `TAG_TRIGGER_MISMATCH` | 【登場時】等の見出しに対応する能力トリガーが無い | 能力の脱落・トリガー誤認 |
| W | `TAG_CONTEXT_MISSING` | 【ターン1回】【ドン!!×N】等に対応する条件が無い | 条件の脱落 |
| W | `DRAIN_LIMIT` | 対話が 30 応答で終わらない | 無限ループ |
| I | `FIRED_EMPTY` / `DEFERRED` / `PARSER_LEGACY` | 対象 0 枚で実行／後の出来事で実行（置換・ターン終了時）／レガシー解析 | 参考。レビューで中身を確認 |

### 3. 意味のレビュー（1 枚ずつ）

```bash
python tests/scripts/card_effect_audit.py show OP01-016 OP09-081 --events
python tests/scripts/card_effect_audit.py list --level EW          # E/W のあるカード
python tests/scripts/card_effect_audit.py list --state UNREVIEWED,TEXT_CHANGED,IMPL_CHANGED --oneline
```

`show` は本文・能力ごとのトリガー／条件・アクション（種別・対象の**非既定の欄を全て**・値・期間・行き先・任意）・
各アクションの実行状況（`[FIRED]` 等）・プローブのイベント列を出す。これを見て、**本文を句に
分解し、句ごとに対応を確かめる**:

1. **句の列挙**: 見出し（トリガー・【ターン1回】・【ドン!!×N】・【自分のターン中】）／条件（「〜の場合」）／
   コスト（「:」の前・「〜できる」）／動作（「、」「その後、」「そうした場合、」で区切る）／
   選択肢（「以下から1つを選ぶ」の「・」）／期間（「このターン中」「次の相手のエンドフェイズ終了時まで」）。
   **本文の句が 1 つでも対応するノードを持たなければ ng**（「何か起きている」では足りない）。
2. **句 ↔ ノードの対応**: 各句について、ノードの種別・対象（自分／相手・ゾーン・種類・特徴・名前・
   コスト／パワー範囲・レスト状態・枚数・「まで」）・値（固定／「N枚につき」の動的値）・期間・
   行き先（上／下・表向き）・任意／必須が本文と一致するか。
3. **構造**: 「その後、」が全選択肢・全分岐にかかるか（選択肢の 1 つにだけ入っていないか）、
   先頭の条件が後続まで支配するか（`docs/TEST_SPEC.md` §8.3 カテゴリH）、「そうした場合」が
   直前の任意動作に掛かっているか、Choice の選択者（自分／相手）が本文どおりか。
4. **実行**: 各アクションが `[FIRED]`（または妥当な理由のある `DEFERRED`・`FIRED_VIA_INTERACTION`）か、
   イベントの値・行き先が本文と合うか。`NOT_FIRED`・`FIRED_EMPTY` は理由を特定する
   （プローブ盤面の限界なら note に書く）。
5. **既知のバグ類型**を当てる: `docs/TEST_SPEC.md` §8.3（複合句の取りこぼし・条件の退化・対象フィルタの
   誤り・持続時間の写像漏れ・スケール値の脱落・危険な常在）と §8.4 のチェックリスト。

判定は 2 値: **ok**＝全句が対応し、構造と実行が本文どおり／**ng**＝どれかが違う（note に
「どの句が・どう違うか」を 1 行で）。E の指摘があるカードを ok にするのは、誤検出と確かめた
ときだけ（`--force` と note に理由）。

### 4. 台帳への記録

```bash
python tests/scripts/card_effect_audit.py record OP01-016 OP04-036 --verdict ok
python tests/scripts/card_effect_audit.py record OP09-081 --verdict ng --note "常在の自己無効が ON_PLAY 能力になっている"
python tests/scripts/card_effect_audit.py record --from /tmp/card_effect_audit/verdicts.jsonl   # 一括
python tests/scripts/card_effect_audit.py status
```

台帳（`tests/fixtures/card_audit_ledger.json`）は 1 枚ごとに判定・日付・note と指紋 3 つ
（本文 `text_sha`・解析結果 `ast_sha`・プローブのイベント列 `probe_sha`）を持つ。指紋は
**直近の scan のもの**が入る＝記録の前に、そのカードを含む scan を回しておくこと。

- 本文が変わる → `TEXT_CHANGED`（再レビュー）
- パーサ／エンジンの変更で解析結果や挙動が変わる → `IMPL_CHANGED`（再レビュー。修正したカードはここに来る）
- `ng` は確認済みでも scan の既定対象に残る（直ったかを毎回見る）

台帳はリポジトリにコミットする（次のセッション・次の差し替えへ引き継ぐため）。

### 5. 大量のカード（全走査・大型の差し替え）

意味のレビューは 1 枚ずつ読むので、数百枚を超えるときは**サブエージェントに分担**する:

1. `list --oneline` で対象を取り、品番の接頭辞ごと（または 40 枚前後ずつ）に分ける。
2. 各サブエージェントには **`reviewer_prompt.md`（このディレクトリ）をひな形として渡す**（句ごとの対応表を書かせ、
   QUALIFIER_GAP を 1 件ずつ決着させる厳格版。**浅い指示だと ok の見逃しが約 1 割・ng の誤判定も出る**＝
   2026-10-01 の pilot で実測）。判定は 1 行 1 枚の JSONL。**台帳には書かせない**。迷ったら ng にして理由を note に。
   E/W のあるカードはまとめて 1 人に渡す（類型が揃うので比較しやすい）。
3. コーディネータ（自分）が JSONL を 1 ファイルにまとめ、ng と E 付き ok を自分で読み直してから
   `record --from` で記録する。
4. 1 セッションで終わらなくてよい。台帳があるので、次は `make card-audit` が残りだけを出す。
   進捗は `status` で報告する。

**分担の運用（2026-10-01 の実績）**:

- バッチは 40 枚前後・8 並列が目安（1 人あたり約 12 万トークン・約 3 分）。品番は
  `list --state UNREVIEWED,TEXT_CHANGED,IMPL_CHANGED --oneline` で取り、`/tmp/card_effect_audit/batches/bNN.txt` に置く。
- サブエージェントは `verdicts_v2_bNN.jsonl` を書く。**集計時に必ず確認する**: 担当全カード分があるか（欠け・余り）、
  ng の note に「どの句が・どう違うか・パーサ/エンジン」があるか、**ok を無作為に数枚抜き取って自分で `show` を読む**。
- 台帳に記録する ok には `[厳格レビュー]` の注記を付ける（浅いレビューの ok と区別するため）。
- 旧台帳の判定と食い違う場合は、新しい（厳格な）判定が正。ng→ok に覆った理由は多くが「`show` に出ない欄」だった
  （`show` は直した）。

### 6. 見つかった欠陥の扱い

**修正はユーザの指示を待つ**（この skill の既定は「洗い出して報告し、台帳に ng で残す」まで）。
直すときは:

- パーサ（`opcg_sim/src/effects/`）とエンジン（`rust/opcg_engine/`）のどちらの問題か切り分ける
  （解析結果が本文と違う＝パーサ／解析結果は正しいのに動かない＝エンジン）。
- 直したら `make card-audit CARD_AUDIT_ARGS="--cards <修正したカード>"` で指摘が消えたことを確かめ、
  `show` で再レビューして ok を記録する。
- 挙動が変わるので `make golden-audit`（差分は**修正したカードの分だけか**を必ずレビュー）→
  `make test` → `make audit-cross`（CLAUDE.md・`docs/TEST_SPEC.md` §5.0）。

### 6.5 修正→再レビューの実績と運用（2026-10-01・初回の全走査）

- 初回の全走査で ng 330 枚 → 修正 3 波（作業パッケージ A〜F の並行・G1〜G3）→ **再レビュー 2 回**で ng 9 枚まで減った
  （各波とも「直す→golden 再生成→`make test`→`make audit-cross`→ng＋IMPL_CHANGED を厳格に再レビュー→`record`」）。
- **欠陥の主な類型**（新カードでも出やすい）: ①連用句の期間・主語の継承漏れ（「このバトル中、〜を得て、パワー+N」の
  後句が INSTANT／任意の自キャラ選択になる）②反応型の誘発句（「〜された時／離れた時」）にエンジンの誘発が無い
  ③置換の適用範囲・任意（断る）④「N枚につき」「直前の枚数」「付与ドン!!数」の倍率・参照 ⑤相手が決める確認・並び替えの
  chooser ⑥「1枚ずつ／残りは」の分配 ⑦条件の範囲（能力全体か一句か）。
- **並行修正の運用**: 作業パッケージ（類型ごと・約 15〜40 枚）を worktree 隔離のエージェントに配る。専用 wheel
  （`pip install --target`）・golden／台帳は触らせない・最後に中央で統合して golden を 1 回だけ再生成する。
  同時に 6 本走らせると API のレート制限で落ちた＝**並列は 3〜4 本まで**。
- **再レビューの判定は浅くなりやすい**: 40 枚を 70〜120 秒で返す批評者は「全句が show と一致」と書くだけになる。
  ng 候補と複数句カードは句→ノード→一致/不一致の表を必須にし、**ok から数枚を自分で `show` して抜き取る**。
- 統合時は parser.py／atoms.py／rules.rs／resolver.rs／triggers.rs／cond.rs が衝突しやすい（解消後に必ず
  `cargo test`＋パーサのテスト。表現が変わったテスト期待値は直す）。

**ng 1 枚だった OP15-074（ユーザ確認で「条件は能力全体に係る」＝現行どおり ok にした）**: 「リーダーが〜の場合、A。その後、B」の条件が
「その後」まで能力全体を支配する扱いは、プロジェクト既定の裁定（`_lift_h_gate`・同型 約 119 能力・
`test_structural_gate` で上限 0 のラチェット）。個別に変えると類型の裁定が割れるため、ルール裁定を決めたうえで
類型ごと直す別作業にする（直すときは `_lift_h_gate` と構造ゲートを一緒に）。

**3 回目の修正（2026-10-01）で解消した旧 ng**: OP13-001（任意の枚数＝0〜N の SELECT_TARGET）・OP15-093（属性付与
＝`ATTR:斬` の一時フラグ）・OP16-079（登場した時の `trigger_subject`）・OP02-002・OP07-083・OP11-024・OP15-031・
OP11-110（コード側は元から正しかった）。「新しい対話・誘発・属性付与が要る」と見えた欠陥も、既存の語彙
（SELECT_TARGET・PASSIVE リスナー・timed_flags）に載せれば直せた——**直せないと判断する前に、符号化に触れない
載せ方を探す**。

### 7. 報告の形

ユーザへは次の順で短く:

1. DB 差分（追加・本文変更・削除の枚数と主な品番）
2. `LOAD_FAIL`／`UNKNOWN_TAG`（新しい仕組み）があればその内容
3. ng のカード一覧（品番・名前・どの句がどう違うか・パーサ／エンジンのどちらか）
4. 台帳の進捗（`status` の数字）

## これまでに見つかった欠陥の類型（レビューの勘所・2026-10-01 初回の全カード点検 2,518 枚）

初回の全点検の結果: **ng 497・ok 2,021**（効果ありカード 2,518 枚）。ng の主な類型（重複あり）: 任意（できる）の脱落 84・
元々のコスト/パワー（欄なし）62・置換効果の範囲/限定 51・HEAL がライフの下に積む 43・ライフの上か下の選択なし 43・
好きな順番の並び替えなし 41・【速攻:キャラ】【ブロック不可】未処理 31・誘発条件の欠落 30・ドン!!の数え方 29。
ok の判定は厳格レビュー（サブエージェント 1 回）で、抜き取りでは見落としが数%ありうる。

- **限定語の脱落**（最多）: 「元々の」（パワー・コスト・効果のない）・「〜以外」・色・「含む特徴」・「相手の効果で」・属性。
  「元々のコスト」は対応する欄がエンジンに無い（本文にあれば常に ng）。
- **「上か下」「好きな順番で」の脱落**（コスト側にも出る）。
- **条件の反転・取り違え**: 「〜がいない場合」の否定落ち、「表向きのライフがある」が枚数 0 の判定になる。
- **「AかB」「AとB」の構造の固定化**（OR が AND になる・2 つ目の対象が脱落）。
- **任意（できる／てもよい）の脱落**: 強制実行になる。
- **句の脱落**: 区切り無しの 2 つ目の見出しの能力・「以下から1つ」の前の句（引く等）。
- **エンジン**: `HEAL`（デッキの上から1枚をライフの上に加える）がライフの**一番下**に積む（`ops.rs deck_to_life`・
  Python エンジン由来）。【速攻:キャラ】【ブロック不可】が未処理。「アクティブの」ドン!!の限定が効かない。
- **置換効果の適用範囲（エンジン共通）**: `find_replacement`（`rules.rs`）は保護者を「除去されるカード自身→リーダー→場の他キャラ」と
  走査し、「このキャラが場を離れる場合」の**自己限定を見ない**（コード読みのみ・実機未確認）。自己置換カードは全て ng 扱い
  （`[置換の適用範囲]` タグ）。「相手の効果で」「特徴《X》」「【相手のターン中】」の限定も条件に載らず raw_text 頼み。
  なお「キャラの『X』がいる場合この効果は無効」は `self_negating_name` で実装済み（RULE_PROCESSING の no-op に見えても ng ではない）。
- **効果除去の置換が任意（「代わりに〜できる」）にならない（エンジンの構造的な欠落・約 30 枚）**: バトル KO の置換は
  `sub_effect.is_optional` を見て確認を先に挟む（accept→置換・decline→KO）が、効果除去（status=LEAVE 等）の経路には
  「確認先行」が無い。任意にすると「断れば無償で守られる」不具合になるので、パーサは BATTLE_KO の置換だけ任意にしている。
  直すには `run_target_loop` に確認の中断（decline 時に元の除去を続行）を足す必要がある。
- **「ドン!!」の数え方**: 「レストのドン!!」「アクティブのドン!!」が総数（アクティブ・レスト・付与の合計）で数えられる、
  「相手のドン!!が自分より多い」の向きが逆（`DON_COUNT_COMPARE`）。
- `show` に出ない欄（`is_vanilla`・`power_min`・`count_dynamic`・`ref_id`・`flags`）を読み落として誤判定する
  （`show` は全欄表示に直した）。

## プローブの仕組みと限界（判定の前に知っておくこと）

Rust の `opcg_engine.effect_probe` は監査 golden と同じ汎用盤面で能力を発動し、

- **条件を真に固定**（else 側がある能力は偽でも回す）
- **対象の絞り込みをカード種別だけにする**（特徴・名前・色・コスト・パワー・レスト状態は見ない）
- **選べるだけ選ぶ**・任意効果は実行する・**入れ子を含む全選択肢の経路**を回す（上限 32 経路）
- 盤面に両者のイベント 2・ステージ 1（手札・トラッシュ）、ステージ置き場、表向きのライフ（上と下）を足し、検査対象がイベントなら場ではなく手札に置き（場の空きを確保）、P1 のリーダーに付与ドン!! 2 枚を付ける

で最後まで解決する。よって次は**プローブでは確かめられない**＝レビューで解析結果を読んで判断する:

- 対象の絞り込み（特徴・コスト範囲など）が本文どおりか（緩めて回しているので実行状況には出ない）
