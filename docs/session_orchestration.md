# セッション並列運用（親セッションから子セッションを起動する）

Claude Code のリモートセッションから、**別のリモートセッション＝別コンテナ**を起動して並列に作業させるための
運用手順。CPU 律速の作業（自己対戦サンプリング、shard 分割した学習データ生成）を複数コンテナに分散する用途を想定する。

検証は 2026-08-13〜14 に実施。**実測で確認できた事実と、確認できなかった事実を明示的に分けて書く**。

ここで扱うのは**起動と回収の経路だけ**。個々のワーカーに何をさせるかは
`*_worker_prompt.md`（例: [`test_worker_prompt.md`](test_worker_prompt.md)）側に書く。

## 1. 前提

- 実行環境は `anthropic_cloud`。環境は `list_environments` で取得する（本アカウントでは "post" の1つのみ）。
- コンテナはセッションごとに独立。**リポジトリはセッション開始時に fresh clone される**。
  一定時間の無操作でコンテナは回収される。
- 親のワーキングツリーの未コミット変更は子に引き継がれない。
- **親子でファイルシステムは共有されない。共有されるのは git のリモートだけ。**
  `/home` に置いたファイル・実行ログ・`pip install` した依存は、そのセッションが消えると一緒に消える。
  **残したいものは commit して push するまで存在しない。**

## 2. ツール

MCP サーバ `claude-code-remote` が提供する。

| 目的 | ツール | 副作用 |
|---|---|---|
| 子セッション起動 | `create_session` | **あり**（コンテナ作成） |
| 状態確認 | `get_session` / `list_sessions` | なし |
| 環境一覧 | `list_environments` | なし |
| 起動済みセッションへの追加指示 | `create_trigger` + `fire_trigger` | あり |
| 中断 | `interrupt_session` | あり |
| 後片付け | `archive_session` | あり |

> **ツール名が2表記ある。** `mcp__Claude_Code_Remote__<tool>` と `mcp__<uuid>__<tool>` の両方が観測された
> （同一セッション内で前者から後者へ切り替わった実例あり。切り替わり後は前者が
> `No such tool available` になる）。`.claude/settings.json` の allowlist は**両方を登録**しないと
> 承認プロンプトを抑止できない。UUID が環境ごとに変わる場合は追記が必要。

> **`create_session` の承認は allowlist で消せない**（2026-08-14 実測）。同じ `allow` 配列に同じ2表記で
> 登録しても、**読み取り系（`list_sessions` 等）は承認なしで通るのに `create_session` だけポップアップが出る**。
> ポップアップの選択肢が「一度だけ許可 / 拒否」のみで**「常に許可」が無い**こと、失敗時のエラーが
> サーバ側が返す形式の `MCP error -32003: MCP tool call requires approval` であることから、
> **サーバ側が毎回の承認を要求している**と考えられる（クライアント側の設定では抑止できない）。
> 断定はできないが、allowlist に項目を足しても解決しないので**時間を使わないこと**。
> 並列で N 件起動するなら承認を N 回押す前提で運用する（起動時の1回だけで、子の作業中は追加で聞かれない）。
> 未確認の回避策＝アプリでセッションを開始するときの permission mode を強くする（§6）。

## 3. 手順

### 3.1 起動

```
create_session(
  title:           "<識別しやすい名前>",
  tags:            ["<グループ名>"],          # 後で list_sessions のフィルタに使う
  source_url:      "https://github.com/gx5gyqe2-art/opcg-sim-backend",
  source_revision: "refs/heads/main",
  outcome_branch:  "claude/<作業ごとに一意な名前>",
  prompt:          "<完全に自己完結した指示>"
)
```

- **`source_url` / `source_revision` は明示する。** 省略すると `session_context.sources` が空のまま返り、
  リポジトリが利用可能かが不定になる。`source_revision` を省くと既定ブランチになるので、
  対象ブランチは必ず書く。
- **`environment_id` は省略する。** 親と同じ環境を継承する（環境変数・ネットワークポリシーも同じ）。
- **`outcome_branch` はワーカーごとに変える。** 同一ブランチへの同時 push は衝突する。
- **`permission_mode` は指定しない。** 親のモードを継承する。親より強いモードを渡すと
  `exceeds parent session's "default"` で**起動そのものが失敗する**。子に強い権限が要るなら、
  親セッションをアプリ側で強いモードで開始しておく。
  とくに **`"plan"` は使ってはいけない**——人間の承認待ちで止まるため、誰も見ていないワーカーは
  そこで永久に停止する。
- **`prompt` は完全に自己完結させる。** 子は親の会話を一切知らない。
- **`model` は省略すると親を継承する**（実測: 子4件とも `claude-opus-5`）。**明示指定も有効**
  （実測 2026-08-14: `model: "claude-sonnet-5"` で起動した子は `session_context.model` /
  `external_metadata.last_served_model` とも `claude-sonnet-5`）。既定は `claude-opus-5` とし、
  機械的な作業を大量に流すときだけ軽いモデルを検討する。
- 並列で起動するときは**同一メッセージ内で複数の `create_session` を発行**する。

### 3.2 進捗の確認

`get_session` の `session_status` は `PENDING → RUNNING → IDLE` と遷移する。
`task_summary`（実行中）と `post_turn_summary`（完了後）に短い要約が入る。
`list_sessions` は `tags` で絞り込める（起動時に付けておく）。

**子の完了を待つために `sleep` でポーリングしない。** 親は他の作業を進め、必要なときに
`get_session` を叩くか、成果ブランチの出現を待つ。

### 3.3 成果の受け取り

**子の成果を親へ渡す経路は git push のみ。**

`post_turn_summary` は**別途生成される要約であり、子の最終メッセージの転記ではない**。
プロンプトで出力形式を指定しても無視される（2回の実測で確認）。「進んだ／終わった」の粗い進捗表示専用で、
**データの受け渡しには使えない**。

したがって、親が読む必要のある値は必ずファイルに書かせて push させ、親は `git fetch` して読む。

```
git fetch origin <branch>
git show FETCH_HEAD:<path>
```

### 3.4 起動後の追加指示

```
create_trigger(name: "...", persistent_session_id: "<子のID>", prompt: "<追加指示>")
fire_trigger(trigger_id: "<trig_...>")
```

`cron_expression` / `run_once_at` を省略すると自走しない poke 専用トリガになる。
実測で `fire_trigger` の**1秒後**に対象セッションが反応した。

**会話コンテキストは継続する**（実測: 初回の `cache_write` 79,987 トークンと、poke 後の
`cache_read` 79,987 トークンが完全一致）。「さっきの続きで」という指示が通る。

> **`send_message` という別経路もあるらしい。** `create_session` のツール説明はこれに言及しているが、
> **検証時のセッションには存在しなかった**（`ToolSearch` で確認・`ListAgents` も "No reachable agents"）。
> 別のセッションでは使えたという報告があるため、**セッションによってツールの顔ぶれが違う**可能性が高い。
> 使えるなら `send_message` の方が簡単。無ければ上の `create_trigger` + `fire_trigger` で確実に通る。

> **制約**: trigger 経由で起こされたセッションは **MCP ツールを持たない**（作成時に警告が出る）。
> 標準ツール（Bash/Read/Write 等）のみ。**poke で起こした子に孫セッションを起動させることはできない。**
> 多段運用が要るなら `create_session` の初回 prompt で完結させる。

### 3.5 後片付け

- トリガ: `delete_trigger`
- セッション: `archive_session`（**archive すると会話内容が読めなくなる**。値を確認してから実行する）
- 作業ブランチ: 下記「既知の制約」を参照

## 4. 実測値（2026-08-13）

| 項目 | 実測 |
|---|---|
| 起動〜完了（repo なし・コマンド数本） | 19秒 |
| 起動〜clone〜commit〜push 完了 | 40秒 |
| `fire_trigger` 〜 対象セッションの反応 | 1秒 |
| poke 〜 完了 | 21秒 |
| コンテナ仕様（親・子とも） | nproc=4 / mem 15GB |

親と子で `/proc/sys/kernel/random/boot_id` が異なることを確認済み（親 `e5bb0c60…` / 子 `65ffd870…`）＝
**別コンテナであることは実証済み**。

### 4.1 3件同時起動時の CPU 分離（2026-08-14 実測）

子3件（C1/C2/C3）を同一メッセージ内で並列起動し、各コンテナで SHA-256 を30秒回して反復数を測った。

| shard | boot_id | nproc | start_epoch | end_epoch | iterations / 30s |
|---|---|---|---|---|---|
| c1 | `0c966c49…` | 4 | 1786672684.14 | 1786672714.18 | **60,107,000** |
| c2 | `8a3aa5b4…` | 4 | 1786672684.06 | 1786672714.11 | **76,932,000** |
| c3 | `9189e216…` | 4 | 1786672694.02 | 1786672724.07 | **72,556,000** |

**判定: CPU は分離されている。**

1. **直列化していない。** 3件の実行区間は `1786672694.02 〜 1786672714.11` の **20.09秒**が完全に重なる
   （C1/C2 は30秒ほぼ全域が重複、C3 のみ起動が約10秒遅れた）。
2. **物理コアの取り合いは観測されなかった。** 単独実行時の基準値 40,125,000 反復に対し、
   3件同時でも **1.50〜1.92倍**（平均 69,865,000）と**むしろ速い**。競合していれば基準値を割るはずで、
   逆の結果になった。
3. **boot_id は3件とも相異なる**＝それぞれ独立したコンテナ。

> **ただしコンテナごとの CPU 性能はばらつく。** 3件の反復数の開きは **24%**（60.1M 〜 76.9M）あり、
> さらに単独実行時の基準値 40,125,000 は3件のいずれよりも大幅に低い。
> **この原因は §4.2 で特定した＝割り当てられる物理 CPU の型が2種類あり、性能が約2倍違う。**
> **シャードに均等な仕事量を配ると完了時刻は揃わない**前提で設計する。
> 起動タイミングも揃わない（今回 C3 は約10秒遅れ）。

### 4.2 5件同時起動・5分連続実行（2026-08-14 実測）

子5件（p1〜p5）を同一メッセージ内で並列起動し、各コンテナで SHA-256 を **30秒 × 10バケット＝5分**
連続で回した。§4.1 に対し「件数を5件へ」「測定を30秒から5分へ」「`/proc/cpuinfo` の model name を追加」
の3点を変えている。

| shard | cpu_model | boot_id | start_epoch | end_epoch | bucket0 | bucket9 | 10バケット平均 |
|---|---|---|---|---|---|---|---|
| p1 | Xeon @ **2.80GHz** | `263a86c5…` | 1786677605.57 | 1786677905.62 | 38,451,000 | 38,277,000 | **38,388,700** |
| p2 | Xeon @ **2.10GHz** | `a1a23d43…` | 1786677609.37 | 1786677909.42 | 75,831,000 | 77,833,000 | **77,882,900** |
| p3 | Xeon @ **2.80GHz** | `3068c0e2…` | 1786677615.53 | 1786677915.60 | 39,056,000 | 38,334,000 | **38,532,400** |
| p4 | Xeon @ **2.10GHz** | `93327843…` | 1786677611.03 | 1786677911.09 | 79,334,000 | 75,465,000 | **77,181,000** |
| p5 | Xeon @ **2.80GHz** | `0f437cff…` | 1786677618.64 | 1786677918.70 | 38,989,000 | 38,683,000 | **38,899,800** |

（`nproc` は5件とも 4。`boot_id` は5件とも相異なる＝すべて独立コンテナ。単位はいずれも 反復数/30秒）

#### (a) 性能ばらつきの原因＝**割り当て CPU の型の違い**（ホスト負荷ではない）

`cpu_model` は**5件で一致しなかった**。2種類が混在し、**反復数はこの2種類でぴったり2群に分かれる**。

| CPU 群 | 該当 shard | 平均 | 群内のばらつき |
|---|---|---|---|
| Xeon @ 2.80GHz | p1 / p3 / p5 | 38.39M / 38.53M / 38.90M | **1.3%** |
| Xeon @ 2.10GHz | p2 / p4 | 77.88M / 77.18M | **0.9%** |

同じ CPU 群の中では平均が **1.3% 以内**に収まる。群をまたぐと **約2.01倍**。
つまり**ばらつきはホスト負荷のノイズではなく、どちらの CPU を引くかで決まる**。

> **`model name` の GHz 表記は性能の指標にならない。** 表記が低い **2.10GHz の方が 2.80GHz より約2倍速い**
> （2.10GHz 側が新しい世代で IPC が高いものと思われるが、`model name` に世代名が出ないため確証は無い）。
> **判別に使えるのは文字列としての `model name` だけで、数値の大小で速い方を推定してはいけない。**

これで §4.1 の「単独実行時の基準値 40,125,000 が3件同時のいずれより低い」も説明がつく——
40.1M は 2.80GHz 群の値（38〜39M）とほぼ一致する。基準値の測定が遅い側のコンテナに当たっていただけで、
競合による低下ではなかった。ただし §4.1 の C1（60.1M）はどちらの群にも一致せず、**未説明のまま**
（当時 `cpu_model` を記録していないため事後の判定は不可能）。

#### (b) 5件同時でも分離は保たれる

- **実行区間はほぼ全域が重なる。** 5件全部が同時に走っていたのは
  `1786677618.64`（最後発 p5 の開始）〜 `1786677905.62`（最先着 p1 の終了）の **286.99秒**。
  各シャードの実行時間は約 300.06 秒なので、**5件が完全同時だった割合は 95.6%**。
- **反復数は §4.1（3件同時）から落ちていない。** 2.10GHz 群は 72.9M〜89.5M で
  §4.1 の 60.1M〜76.9M を**上回り**、2.80GHz 群は 37.5M〜39.3M で単独実行時の基準値
  40.1M とほぼ同じ。**件数を3→5に増やしたことによる低下は観測されなかった。**
- **起動は揃わない。** 開始時刻の散らばりは **13.07秒**（p1 が最速、p5 が 13 秒遅れ）。
  §4.1 の約10秒差と同程度。

#### (c) 5分連続でもスロットリングは入らない

bucket0 → bucket9 の変化と、10バケット中の最大−最小:

| shard | bucket0→bucket9 | バケット間の振れ幅 | 単調減少か |
|---|---|---|---|
| p1 | −0.45% | 3.4% | いいえ（最小は bucket7） |
| p2 | **+2.6%** | 21.4% | いいえ（最大は bucket6） |
| p3 | −1.85% | 3.3% | いいえ |
| p4 | −4.88% | 12.5% | いいえ（最大は bucket3） |
| p5 | −0.78% | 1.5% | いいえ |

**5件とも単調減少していない**＝5分スケールでのスロットリングは観測されなかった。
最大の変化幅も p4 の −4.9% にとどまる。

> 副次的な観測として、**速い 2.10GHz 群の方がバケット間の振れが大きい**（12〜21% 対 1.5〜3.4%）。
> 遅い群は極めて安定している。原因は未特定。

## 5. 既知の制約

1. **成果の受け渡しは git push のみ**（§3.3）。
2. **レート制限はアカウント共有**（`five_hour` ウィンドウ）。並列数を増やしても総スループットは頭打ちになる。
   ワーカーを大量に並べるより、**「10分の待ちを1本だけ肩代わりさせる」用途が最も割に合う**。
3. **子から親へのメッセージ経路は無い。** `ListAgents` は "No reachable agents" を返す。
   親は `get_session` のポーリングか push されたコミットでしか状況を知れない。
4. **子のツール権限は親を超えられない。** `extra_allowed_tools` に親が持たないものを書いても落とされる。
5. **同一ブランチへの同時 push は衝突する。** シャードごとにブランチを分けるか、
   書き込むファイルを完全に分離する。
6. **リモートブランチの削除ができない。** `git push origin --delete <branch>` は
   **`RPC failed; HTTP 403`** → `send-pack: unexpected disconnect` で失敗する
   （2026-08-14 に別セッションで再現。403 が返るのでセッションの git proxy が削除操作を拒否している）。
   **GitHub MCP 側にもブランチ削除ツールは無い**（`create_branch` はあるが対になる delete が無い）。
   リトライしても通らないので深追いしない。テスト用ブランチは GitHub 側で手動削除する。
7. **`~/.claude/projects/` に過去セッションの transcript は残らない。** コンテナが毎回作り直されるため。
   履歴走査に依存する仕組み（`/fewer-permission-prompts` 等）はこの環境では機能しない。
8. **子は依存が入っていない素のコンテナで始まる。** ワーカープロンプトは `pip install` から書く
   （`pytest` すら入っていない）。
9. **子には報告だけさせる方が安全。** 「失敗したら直せ」と書かない限り修正させない。
   何が原因で落ちたのかが追えなくなるため、修正は結果を見た親（または人間）が判断する。
10. **`.claude/settings.local.json` は永続しない**（gitignore 対象＝新コンテナに存在しない）。
   allowlist を永続させるには**リポジトリにコミットする `.claude/settings.json`** を使う。
   さらに、**その設定は子が clone するブランチに存在していなければ効かない**——作業ブランチに
   置いたままでは `main` から始まるセッションに届かないので、**allowlist の変更は main へ入れる**。
   反映は**次のセッションから**（settings はセッション開始時に読まれる）。
   **読み取り系への実効性は 2026-08-14 に確認済み**——`.claude/settings.json` を main へマージした後の
   新規セッションで `list_sessions` が承認プロンプト無しに通った（解決されたツール名は
   `mcp__Claude_Code_Remote__*` 表記の方）。**ただし `create_session` は同じ設定でも承認を求められる**（次項）。
11. **`create_session` の承認プロンプトは消せない**（§2）。allowlist が効くのは読み取り系のみ。
   同じ設定下で `list_sessions` は無音で通るのに `create_session` はポップアップが出ることを、
   2026-08-14 のセッション（§4.2 の測定を実行したもの）で確認している。
   **エージェント側からは「承認された呼び出し」と「承認が不要だった呼び出し」が区別できない**ため、
   実行ログだけを見て「プロンプトが出なかった」と判断してはいけない。
12. **コンテナの CPU 性能は約2倍ばらつき、選べない**（§4.2）。**均等なシャード分割は完了時刻を揃えない。**
   締め切りのある並列処理では、静的に等分するのではなく**ワークキュー型（速い子が多く取る）**にするか、
   最も遅い群（Xeon @ 2.80GHz 相当）の速度を前提に見積もる。

## 6. 未検証

2026-08-14 の検証で、`model` 明示指定（→ §3.1）、3件同時起動時の CPU 分離（→ §4.1）、
性能ばらつきの原因・5件同時での分離・5分連続でのスロットリング（→ §4.2）はいずれも解消した。
残っているのは以下。

- **6件以上でも分離が保たれるか。** 実測は5件まで。5件時点では低下の兆候が全く無いため
  頭打ちの位置は分かっていない。
- **数十分〜数時間のスケールでスロットリングが入るか。** 実測は連続5分まで。
  5分では単調減少が一切出なかったが、それ以上の時間は未測定。
- **割り当てられる CPU の型を選べるか / 事前に知れるか。** §4.2 のとおり2種類あり性能が約2倍違うが、
  `create_session` に希望を伝える手段は見つかっていない。**起動してから `/proc/cpuinfo` を読むまで
  どちらを引いたか分からない。** 引き直し（archive して再起動）で狙えるかも未検証。
- **2つの CPU 群の出現比率。** 5件で 2.80GHz が3件・2.10GHz が2件だったが、
  1回の観測なので比率としては当てにならない。
- **速い 2.10GHz 群でバケット間の振れが大きい理由**（§4.2 (c) の副次観測）。
- **§4.1 の C1 が記録した 60.1M がどちらの CPU 群にも一致しない理由。** 当時 `cpu_model` を
  記録していないため事後の特定は不可能。
- **`create_session` の承認プロンプトを permission mode で消せるか。** §2 のとおり allowlist では消せない。
  承認要求がサーバ発ならクライアント側の設定では消せないが、クライアント発なら消える可能性がある。
  確認方法＝アプリでセッションを開始するときの permission mode を強いもの（`dontAsk` /
  `bypassPermissions` 等）にして `create_session` を呼ぶ。**消えれば「クライアント発」、
  消えなければ「サーバ強制」で確定**する。
