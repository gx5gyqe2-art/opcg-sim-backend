# ライフと手札の交換の定式化（守り・攻めの判断を予算として書く）

2026-09-13 作成。ユーザ指摘「測るというより、懸念を言語化して数式化して定量化できないか」への回答。
**勝率の比較（観測）ではなく、局面ごとの会計（モデル）で判断の良し悪しを言えるようにする**のが目的。
関連: `docs/reports/2026-09-13_time_plan_map.md`（時計 × 方針の地図）・
`2026-09-13_can_or_wont.md`（できない／しないの分離）・`2026-09-12_race_atk.md`（攻撃パワー別の守り）。
**この定式化は上の 2 つの報告の結論を一部覆す**（§6）。

## 1. 交換の恒等式

カウンター窓で、超過パワー x（攻撃側のパワー − 自リーダーのパワー）の攻撃に対し:

| | ライフ | 手札 | その他 |
|---|---|---|---|
| **受ける** | −1 | **+1**（ライフカードが手札へ） | トリガーの期待値 +τ |
| **守る** | ±0 | **−c(x)** | — |

`c(x)` は止めるのに要る枚数（手札のカウンター値の合計が x 以上になる最小の組。全部 1000 なら `⌈x/1000⌉`）。
**受けるのは「ライフを失う」ではなく「ライフ 1 枚を手札 1 枚に変換する」**——ここを落とすと
「受ける＝損」という誤った前提が入る（実際に入っていた）。

## 2. 予算（何回守らなければならないか）

- `L` … 今のライフ（0 になった次の被弾で負け＝**受けられるのは残り L 回**）
- `T` … 決着までの自席ターン数（時間軸ヘッドの `t_left`・誤差 0.73 ターン）
- `A` … 相手の 1 ターンあたりの攻撃回数（相手のリーダー＋起き上がっているキャラ）
- `N ≈ A · T` … これから飛んでくる攻撃の総数
- `B` … ブロッカーで止められる回数
- `H` … 今の手札・`D ≈ T` … これから引く枚数・`K` … 攻めに要る枚数

**必ず守る回数** `G = max(0, N − L − B)`。守りに使える札は `H + (N − G) + D − K`
（`N − G` は受けた回数＝増える札）。したがって**余裕**は

```
S = H + (N − G) + D − K − Σ_{安い G 本} c        （≈ H + (N − G) + T − K − G·c̄）
```

`c̄` は「後で必ず守る攻撃」の平均単価。

## 3. この窓の判断（差を取ると項が消える）

受けた場合と守った場合の S を比べると `H` と `N − G` の項が打ち消えて:

```
S(受ける) − S(守る) = c(x) − c̄
```

**安い攻撃を守り、高い攻撃を受ける**のが予算上の最適。理由: 後で必ず守る枠が G 本あり 1 本 `c̄` 枚
かかる。今の攻撃が平均より高くつくなら、**手札ではなくライフで払う方が安い**。

3 つの領域に分かれる:

| 領域 | 条件 | 最適 |
|---|---|---|
| 1 | `G = 0`（全部受けても生き残る） | **守るのは純粋な無駄**（τ も取りに行ける） |
| 2 | `G > 0` かつ `S ≥ 0` | **`c(x) < c̄` なら守り・`c(x) > c̄` なら受ける** |
| 3 | `S < 0` | どう守っても足りない＝トリガー等の別の出口を狙う |

## 4. しきい値はデッキごとに違う——その値は導ける

ユーザ指摘（2026-09-12）「ライフ 3 が閾値なのは全リーダー平均値では？ リーダー（デッキの中身）別に
しきい値が変わる。3 に強制するのは誤った学習」。**これは定数ではなく式になる**:

```
θ(deck, state) = A · T − B        （L < θ で守りが必須になり始める）
```

- 速いデッキ（`T` 小）→ θ 小 → **守り始めが遅くて正しい**
- 相手が横に並べる（`A` 大）→ θ 大 → **早くから守るのが正しい**
- ブロッカーが多い（`B` 大）→ θ 小

`plan_map_strat` で観測した「山はライフ 2〜4 の帯に共通・帯の中の位置は分解能以下」は、
**`A·T − B` がその帯に落ちること**の現れと読める（A≈1.5・T≈2・B≈0 で θ≈3）。
**固定ライフを強制する案が誤りだったのは「平均だから」ではなく「θ が状態の関数だから」**。

## 5. 記録から計算できる（全部ある）

| 記号 | 出どころ |
|---|---|
| `L` | `scalars[0]` |
| `H` | `scalars[6]` |
| `c(x)`・手札のカウンター総量 | トークンの `counter_value`（S 列 7・手札 10 枠・カウンターイベントも max で入る） |
| `x` | トークンのパワー（攻撃側の最大 − 自リーダー・`race_state._incoming`） |
| `A` | 相手の枠の `can_attack_now`／`power_opp_turn`（S 列 5／20） |
| `B` | 自分の場の `is_blocker_active`（S 列 6） |
| `T` | 時間軸ヘッドの `t_left`（誤差 0.73 ターン）または規則での算術 |
| `τ` | デッキのトリガー密度（`deck_kinds`） |

## 6. これで測るもの（勝率の表を置き換える）

1. **領域の内訳**: 窓が領域 1／2／3 のどれに落ちるか（今の CPU がどこで何をしているか）
2. **順序の誤り**: 領域 2 で `c(x) > c̄` を守り、`c(x) < c̄` を受けた回数（**予算上の誤り**）
3. **予算破りの受け**: 受けた結果 `S < 0` になり、守れば `S ≥ 0` だった行
   （`K = 0`・安い順・τ 無視で見積もる＝**実際の誤りの下限**）

## 7. この定式化が覆す過去の結論（重要）

- **「終盤はもっと守れ」は言い過ぎ**（`2026-09-13_time_plan_map.md`／`can_or_wont.md`）。終盤は `G` が
  大きいので問題は「守るか」ではなく**「どれを守るか」**。誤りがあるとすれば**順序**か**予算破り**。
- **「超過パワーが上がるほど守らない（0.525→0.415）」は式の上では正しい挙動**
  （`2026-09-12_race_atk.md` で「合理と非合理を分離できない」として保留していた）。
  `c(x) > c̄` なら受けるのが最適＝**あの単調減少は合理の側の証拠**。
- **ユーザの 2 つの懸念は別物ではなく同じ式の別の項**: 「ライフから欲しいカードがある」＝ `(N − G)` と `τ`、
  「次ターンのために手札を残す」＝ `G·c̄`。

## 8. 近似と偏りの向き（読むときに必ず添える）

- `K = 0`（攻めに札を使わないと仮定）＝ S を**過大**に見る → 「予算破り」と判定した行は**確実**（下限）。
- 安い順に守れると仮定 ＝ コストを**過小**に見る → 同じ向き（下限を守る）。
- `τ` を無視 ＝ 受けるの価値を**過小**に見る → 「受けたのが誤り」の判定は**保守的でない**（注意）。
  トリガーで攻撃側が消えれば予算は回復しうるので、領域 3 の判断には τ を必ず添える。
- `c(x)` はカウンター 1 枚あたり 2.5（5000）で飽和する符号化を使う＝**過小**評価。
- ブロッカーは「1 回止める」と数える（KO される・攻撃を吸うだけで盤面を失う点は勘定に入らない）。
- `T` は推定（誤差 0.73 ターン）＝ `N = A·T` の誤差は約 `A × 0.73`＝1 本前後。**領域の境界付近は不定**。

## 9. 攻め側の同じ台帳——「7000 理論」はこの式の裏側だった

ユーザ指摘（2026-08-12・`cpu_v54_don_margin_20260812.md`）「過去の経歴から、CPU はドン付与が苦手」と、
そこで言語化された**7000 理論（カウンター 2 枚の強要）**は、§3 の `c(x)` を**攻め側から見たもの**。

攻撃に DON を k 本付けると超過パワーが 1000k 上がり、**守る側の必要枚数が k 枚増える**:

```
pressure(k) = c(x + 1000k) − c(x)      （カウンターが 1000 なら ≈ k）
→ DON 1 本 = 相手の手札 1 枚（守られた場合）／通れば 1 ライフ
```

つまり**DON・ライフ・カウンターはすべて「カード」に換算される同じ台帳**にある。攻め側の最適は
「damage を増やす」ではなく**「相手の予算 S を負にする」**——すなわち `c(x)` を相手が払えない所まで
押し上げること。**7000 を作る手はその離散版**（リーダー 5000 に対し +2000＝カウンター 2 枚の強要）。

- **過剰盛り**（既に境界を超えているのに DON を足す）＝ `pressure(k) = 0` ＝ 純粋な無駄。
  旧実装は逆に「過剰＝無意味」の規則で**7000 を作る手を候補から消していた**（行動空間の穴・v54 で修正）。
- `don_waste`（DON を付けて攻撃しない・`plan_drift` で計測済み）の値段も同じ単位＝
  **付けた本数ぶんの「相手の手札」を取り逃がしている**。

## 10. 「相手ライフが少なくゲームが短いなら受けることもある」（ユーザ指摘 2026-07-11）

`cpu_learned_mark_review_20260711.md` の但し書きは、**§3 の領域 1 そのもの**だった:
相手のライフが少ない＝自分が決めるまでのターン数 `T` が小さい ⇒ `N = A·T` が小さい ⇒
`G = max(0, N − L − B) = 0` ⇒ **受けるのが最適（守るのは無駄）**。
2 か月前に言語化されていた条件を、いま式の中に置いた。

## 11. 中盤の 3 方針は「相手の時計のどの項を攻めるか」（ユーザ言語化 2026-09-12）

自分が決めるまでのターン数 `T_me` と、相手が決めるまでの `T_opp` の競争。勝ち筋は `T_me < T_opp`。

```
T_me  ≈ 相手のライフ / (自分の攻撃回数)      … ただし相手の予算 S_opp が尽きるまでは通らない
T_opp ≈ 自分のライフ / (相手の攻撃回数)      … 同じく自分の予算 S が尽きるまで
```

ユーザが言語化した 3 方針は、**この式のどの項を買うか**の違いだった:

| 方針 | 買うもの | 式の項 |
|---|---|---|
| 純粋な殴り合い | 相手のライフ | `T_me` の分子を直接削る |
| シーソー（キャラ攻撃を混ぜる） | **相手の手札**（カウンターを吐かせる）／相手のキャラ | `S_opp` を削る・`A_opp` を減らす |
| 手札切れ待ち | `H_opp → 0`（そこから `c` が払えない＝全部通る） | `S_opp < 0` を作る |

**キャラへの攻撃は「札を使わない除去」**（ユーザの言い方）＝こちらの手札コスト 0 で、相手に
「カウンターを吐く」か「キャラを失う」の二択を強いる。したがって選択は**交換レートの最大化**:

```
（相手が失う札＋盤面）／（自分が失う札）     … face は自分のコスト 0・相手のコストは min(c(x), ライフ 1)
```

## 12. デッキの属性は `c̄(t)`・`K`・`L/H の再生` の形（ユーザ言語化 2026-09-12）

ユーザが列挙したデッキ別の守りの比重は、**予算のパラメータの形**として書ける:

| ユーザの記述 | 式での意味 | 導かれる最適 |
|---|---|---|
| 後半にパワーを上げる／守りに使えるキャラ／カウンターイベント／無力化 | **`c̄(t)` が時間で下がる**（同じ攻撃を後で安く止められる） | **序盤は受け、後半に守る**（＝記述どおり） |
| キャラを展開して物量で押す | **`K` が大きい**（攻めに札を使う） | 守りに回す札が無い＝受ける |
| 耐久・準耐久（ライフ回復・手札増加） | **`L`・`H` が再生する**＝予算が回復 | 守っても戻るので混ぜられる |
| パワーで押し切る | 相手の攻撃が重い＝**`c(x)` が高い** | 高い攻撃は受ける側に寄る |

**「デッキごとに比重が変わる」は `c̄(t)` の傾きと `K` の大きさで決まる**——`c̄(t)` を記録から
デッキ別に描けば、守り始めの時刻の予測がそのまま出る（未測定）。

## 13. ターンの途中で ①→② に移る＝逐次決定と攻撃順序（ユーザ言語化 2026-09-12）

リーサルの試行は**攻撃 1 本ごとの逐次決定**。1 本ごとに (a) 相手がカウンターを吐いたか＝
`S_opp` の情報が更新され、(b) 自分の残り攻撃回数が減る。したがって

- **打ち切れるかの再計算**: 残りの攻撃で `Σ force > S_opp` を作れなければ、そこで②（ゲームを伸ばす）へ移る
  ＝ユーザの「ターンの最初は①だが途中から②に移る」はこの更新のこと。
- **攻撃順序に option value がある**: 安い攻撃を先に通して相手の予算を測り、重い攻撃を後に残す
  （逆も戦術としてある）。量は `V(最良の順序) − V(最悪の順序)`＝**同じ攻撃集合での順序の価値**。
  強制選択の A/B で測れる（未測定）。

## 14. 「負け濃厚なら最初から無茶をする」＝世界の数の問題（ユーザ言語化 2026-09-12）

勝敗は二値なので `E[z] = 2·P(win) − 1`＝**平均を最大化することは勝率を最大化すること**。
つまり「無茶な攻撃」が正しいときは V も（較正されていれば）それを正しく高く評価する＝
分散を別に扱う必要は無い。**本当の障害は隠れ情報のサンプリング**:

探索は PIMC で **worlds = 4**。相手の手札の引き（トリガー・カウンターの有無）に依存して
「4 世界のうち 1 つでしか勝てない線」は、§7 の検出確率がそのまま効く:

```
P(その線が 1 度でも当たる) = 1 − (1 − p)^4      （p＝勝てる世界の割合）
p = 0.10 → 34%    p = 0.25 → 68%    p = 0.50 → 94%
```

**worlds = 4 では「2 割の世界でしか勝てない線」は半分以上見落とす**——負け濃厚の局面で
必要なのはまさにその線なので、**無茶ができないのは評価ではなく世界の数**という説明になる。
（`docs/measurement.md` §7 と同じ式。`worlds` を上げる費用と合わせて判断する。）

## 16. 「入口コミット」は予算の解き方そのものだった（ユーザ決定 2026-08-15）

`gen15_adoption_20260815.md` の**入口コミット**（`SERVE_BATTLE_COMMIT`・防御プランを窓の入口で
1 回立て、以後は実行のみ・「人間はカウンターを切った後に考え直さない」）は、
**§2 の予算を解くのに必要な形**だった——`Σ_{安い G 本} c` は**そのターンの攻撃を全部見てから**
「どれを守るか」を選ぶ問題で、攻撃 1 本ずつ貪欲に決めると最適にならない。

```
貪欲（1 本ずつ）: 目の前の攻撃を止められるかで決める
最適（入口で 1 回）: そのターンの攻撃集合から**安い G 本**を選ぶ
差 = Σ_{貪欲が選んだ G 本} c − Σ_{安い G 本} c   ≥ 0
```

A/B は当時「同等（wr 0.520・CI [0.451,0.589]）かつ 31% 高速」で、**強さでは差が出なかった**が、
**予算モデルの観点では入口コミットが構造的に正しい**（貪欲との差は上式で測れる・未測定）。

## 17. 攻め側の恒等式は 2026-08-05 にユーザが言語化していた（コード注釈から発見）

`opcg_sim/learned/config.py` の `TREE_BOX_BATTLE` の注釈（2026-08-05・ユーザ指摘）:

> 攻撃の帰結が具体的な出口として立ち上がる＝「相手手札−1（カウンターを絞り出した）」か
> 「相手ライフ−1・手札+1（通した）」かの二択が見えるようになる。**攻撃は必ず相手に損失を強いる
> ので「止められる＝無駄」ではない**

これは**§1 の交換の恒等式を攻め側から書いたもの**そのもの（`c(x)` 枚を吐かせるか、ライフ 1 枚を
手札 1 枚に変換させるか）。当時の処方（木の中の戦闘窓も箱化して出口を立てる）で
**ドン付与の判断が初めて動いた**（m2@44 0.00→0.62・m5@7 0.00→0.56）＝
**「損失を強いる」という見方を出口として持たせた瞬間に打ち手が変わった**という実測がある。

同じ注釈のもう 1 点も記録に値する: 「**二人零和では相手は最善応手を返すのが正しく、PUCT の
訪問混合は収束前の副産物であって設計された保険ではない**」（ユーザ指摘 2026-08-05）＝
窓をミニマックスで畳む根拠。これは実装済み（`TREE_BOX_BATTLE = True`）。

## 18. 守りには**ドンも要る**——`c(x)` は 1 つの通貨で書けていなかった（2026-09-13）

§1〜§17 は守りの費用を「手札 `c` 枚」の 1 通貨で書いた。これは**キャラのカウンターには正しく、
【カウンター】イベントには誤り**。`rules/battle.rs::apply_counter` の裁定:

- **キャラ（イベント以外）** … 印字カウンターを足して手札から捨てる＝**費用は札 1 枚だけ**
- **【カウンター】イベント** … `pay_cost` でコストを払ってから能力を解く＝**札 1 枚＋ドン `k` 個**

符号化は両方を 1 列（`counter_value` = `max(印字, イベントの上げ幅)`）に畳んでいるので、
**予算式の入力として使うと「払えないカウンター」を数に入れてしまう**。正しい形は費用を 2 次元にする:

```
guard(x) = min { (枚数, ドン) : 合計の上げ幅 ≥ x }        費用は (c, k) の 2 成分
払えるか   = k ≤ D_opp_turn                              D＝相手ターン中に起きている自分のドン
```

`D_opp_turn` は**自分のターンの打ち回しで決まる**（使い切ればゼロ）。つまり
**「ドンを残す」という行為が守りの予算に前借りで効く**——これは §11 の「相手の時計のどの項を買うか」
と同じ構造の選択で、今の定式化にはこの項が無かった。

**測り方**（`tests/scripts/guard_afford.py`・台帳 §6）: 手札を無料（印字）と有料（イベント）に分解し、
`D`（`scalars` 列 2）を予算に 0/1 ナップサックを解いて、達成できる上げ幅の上限を出す。
`enough` の旧定義（`counter_value` の合計 ≥ x）との差が、**§5 の表が過大だった分**。

**予備的な観測（8 局のスモーク・要確認）**: 相手ターン中の自分のアクティブなドンは平均 **0.4 個**。
本当なら CPU は自分のターンでドンを使い切っており、**【カウンター】イベントは構造的に打てない**
＝`c(x)` の実効値は印字カウンターだけで決まる。この場合 §5 の `c(x)` は
「手札の印字カウンターの合計」と読み替えるのが正しい。

## 19. `c̄` と τ の実測値（2026-09-13・デッキから直接）

§4 は「`c̄` はデッキごとに違う」と書いたが値が無かった。`tests/scripts/deck_profile.py` で
**デッキの中身だけから**測った（記録も対局も要らない・`docs/reports/2026-09-13_deck_profile.md`）:

| x | `c̄`（合成 800 デッキ） | `c̄`（実デッキ 240） | 止められない確率（合成／実） |
|---|---|---|---|
| 1000 | 1.00 | 1.00 | 0.005 / 0.008 |
| 2000 | 1.28 | 1.40 | 0.024 / 0.057 |
| 3000 | 2.25 | 2.38 | 0.080 / 0.170 |
| 4000 | 2.78 | 2.97 | 0.187 / 0.328 |
| 5000 | 3.63 | 3.84 | 0.353 / 0.503 |

**§9 の攻め側の恒等式の精密化**: 超過パワー +1000 が相手に強いる枚数は **平均 +0.66 枚**
（+1 枚ではない——2000 カウンターが在るため）。**段は一定でない**: `2000→3000` が +0.97 枚で
最も高く、`3000→4000` は +0.53。つまり「7000 に積む」が効くのは
**1 枚で足りない高さへ跨ぐ段**であって、1000 刻みの線形な足し算ではない。
`force`（`attack_budget.py`）を 1000 刻みで数えるとこの段差を平らに潰す＝**枚数で読むときは
この表で変換する**。

**τ とリーダー差**（実デッキ 4 リーダー）: τ は **0.00〜0.50**・`c̄(3000)` は **2.09〜3.00**。
同じ盤面・同じ x でも `c(x) − c̄` の符号が**リーダーによって逆になる**＝
固定のライフしきい値は原理的に誤り（§4 の主張が実測で立った）。

**実デッキは合成より守りが重い**（`c̄` が高く `p_cant` がほぼ 2 倍・カウンター所持率 0.586 対 0.677・
【カウンター】イベントは 6.65 対 3.97 枚＝§18 のドン問題がより効く）。実デッキでの弱さを読むときは
「汎化の失敗」と「予算が厳しい」を分けること。
