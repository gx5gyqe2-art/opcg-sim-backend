# ドン箱化計画（DON_BOX・探索層の配分計画候補・2026-08-12 起案）

L1/G/B 共通の探索層に「ターンのドン予算の**配分計画**」を複合候補（箱）として導入する計画。
`cpu_backbone_plan.md` と同格の生きた計画文書（実装に追従して更新する）。

## 0. 背景 — なぜ箱か（v54 の帰結）

- (C) マージン付与（`don_attach_audit`→v54）は行動空間の穴（人間の付与の53%が候補外）を
  塞ぎ、**ネット無変更でアリーナ +7%**（wr 0.570 CI[0.528,0.612]・200ペア）を確認した。
- ただし現行は付与が**1枚=1手**のため、(a) 深盛りほど探索木で縦に伸びビームで不利、
  (b) 「付与だけして未攻撃」の中間状態を価値ネットが評価する（v50 乖離族の弱点を踏む）、
  (c) 「使わずに残す」（温存）が手として存在しない、という3つの上限が残る。
- 箱化＝「配分済みの盤面」を直接評価させる構造で、(a)(b) を探索構造で回避し (c) を候補化する。
  前例は v35 の戦闘窓の箱化（box_battle）。

## 1. ドンの使い道の分類（ユーザ整理 2026-08-12・正本）

**基本**（箱の最小実装が扱う）
1. **付与**（パワー加算・カウンター強要の打点作り）
2. **キャラクター登場**（コスト支払い＝既存 PLAY 手が扱えている）
3. **イベントカウンター用の相手ターンへの温存**（現状「手」として存在しない＝最大の穴）

**応用**（第2段以降）
4. キャラクター/リーダー効果での使用（起動コスト＝既存 ACTIVATE_MAIN が扱えている）
5. 効果用の相手ターンへの温存（4 のコスト分を残す判断）

## 2. 設計

### 2.1 箱＝配分計画の複合候補

```
DON_BOX = (付与 k 枚 → アタッカー X → 対象 Y へ攻撃, 温存 r 枚)
```

- 探索内部でのみ存在する**マクロ手**。適用時は原始手列（ATTACH_DON×k → ATTACK）へ展開し、
  **記録・再生・API は原始手のまま**＝行動空間の外形を変えない（2026-08-12 の再生忠実度
  修正の教訓: 記録形式を触る変更は分岐バグの温床）。
- 候補は同一深さの兄弟として並ぶ＝「k=0 素攻撃 / k=2 で7000 / 全ドン」が探索予算を
  公平に取り合う。チェーン縦伸びとビーム消耗が消える。

### 2.2 k の列挙（算術・攻撃者×対象ごとに高々3点）

- k_min: 攻撃が通る最小（atk ≥ def になる枚数・0 含む）
- k_2枚: need=3000（カウンター2枚要求＝(C) の帯上限・7000理論）を作る枚数
- k_4k: need=4000（2000×2枚要求）を作る枚数【帯拡張・第2段。(C) 単体では過剰盛りと
  区別できず落としていた領域＝箱化とセットでのみ解禁する】

### 2.3 r（温存）の列挙（自己情報のみ＝公平性契約）

- r ∈ {0} ∪ {自分の手札にあるカウンタータイミングのイベント/起動のコスト}（重複除去・
  高々2〜3点）。「r 残すとこのイベントが相手ターンに撃てる」は列挙時に機械判定できる
  （エンジンの支払可能性と同じ算術・効果の静的解釈ではない）。
- 箱の k は budget − r で上限され、温存が付与と**同じ土俵で競合**する。
- 温存の価値判断は葉の value に委ねる。判断材料は既存の v6（手札資源集約）＋ドン残数＋
  （採用済みなら）v10 Δ の d_opp_def（相手の詰めを守り切れるか）——**測定と配分計画が
  噛み合う**設計。

### 2.4 実装位置と席別 seam

- 候補生成: learned 経路（`adapter.OPCGGame.legal_actions` → 候補合成層）に
  `don_box`（None=config 既定）を追加。L1 への展開は learned で実証後に判断。
- seam: `LearnedEngine(don_box=...)`／`arena_resume --cand-don-box`（(C) の
  `--cand-don-margin`・v35 の `--cand-box` と同じ流儀）＝同一ネット A/B で単独検証。
- MCTS 側: マクロ手の適用は既存 `_apply_move_inplace` の列適用（clone 1回）。
  visit/prior の扱いは通常手と同一（policy prior はマクロ手に均等 or 素攻撃手の prior を
  継承——実装時に A/B）。

### 2.5 訓練整合（train/serve skew の回避）

- 自己対戦生成（dense 系・bb_gen）も同じ候補生成を使うため、箱化 ON のコーパスと
  serve の分布は自動的に一致する。**ON/OFF を跨いだ混合コーパスは作らない**
  （defense_cf v35 の教訓: 片側だけ変えると学習不能教師/分布ずれになる）。

## 3. 検証計画（Go/No-Go）

1. 列挙の単体テスト: k/r の算術（しきい値・予算・温存競合）＋マクロ展開の原始等価性
2. 同一ネット A/B アリーナ（既定ミラー 200ペア）: (C) 単体を上回るか
   （比較基準は (C) 済みの現行＝上乗せを測る）
3. エネル対面 A/B（`don_margin_enel_ab` の箱版）: 温存 r の本場（カウンターイベント＋
   ドン経済）で効くか。v54 の層別（実行中）で (C) 単体がエネルで中立なら、箱化の
   上乗せがここで出るかが本命の検証になる
4. ゲート9点非退行＋ `make test` green
5. 採用後: bb3 コーパスへ反映（B系は箱化された行動分布で学ぶ）

## 4. 段階（現況 2026-08-12）

- **Phase 1**: 攻撃箱（k 算術・r なし）＋ seam ＋ 単体テスト → A/B
  **【済・中立】** 実装 `a4149e7`・A/B 200ペア wr 0.522 CI[0.480,0.565]＝(C)済み基準に上乗せなし
  → 既定 OFF のまま P2 の土台として維持（`cpu_v55_don_box_p1_20260812.md`）。
  読み: (C) が同じ計画をチェーンで到達可能にしており、探索表現の改善だけでは出ない。
  箱化の固有価値＝チェーンで表現できない「温存 r」に集約された。
- **Phase 2**: 温存 r → **【診断で閉じた・実装せず】** `don_reserve_probe` の二帯測定
  （bg_luffy 30点・shanks 3点）で欠陥検出ゼロ＝探索木が相手ターンのカウンター窓まで届いて
  おり温存は既に織り込まれている（`cpu_v56_don_reserve_20260812.md`・再開条件も同報告）。
  設計知見: 温存は行動空間の対象でない（r 注釈は同一盤面＝同一葉）。**基本3はこれで完了**
  （付与=v54・登場=既存・温存=欠陥なし）。以下は当時の試験場検討の記録:
  **試験場の訂正（ユーザ指摘 2026-08-12）**:
  エネルデッキのカウンターイベントは**全て cost0**（神避/放電/神の裁き/雷獣/万雷）＝温存 r は
  p_enel:nami 対面では**不活性**（nami はカウンターイベント 0 枚）。v54 層別の中立は P2 の
  動機にならない。fixture 実査で ドンコスト付きカウンターイベントを持つのは
  **bg_luffy（cost1×8枚）と shanks（cost2×3枚）のみ** → P2 の A/B はこの2デッキが守り側に
  立つ対面で行う。エネル対面の中立の原因は未特定として残す（配り支配 or don!!-X 経済の評価）。
- **Phase 3**: 帯拡張（k_4k）と応用（効果コストの温存）／L1 への展開判断
- 各 Phase とも「実装→単体→A/B→採否」を独立に判定（v44 規約: 買う前に測る）

## 5. リスクと逃がし

- **ビーム希釈**: 箱候補が増えすぎると既存手の探索予算を食う → k/r の列挙点数を
  算術で絞る（§2.2/2.3）・seam で即 OFF 可能
- **policy prior の空白**: マクロ手は学習済み prior を持たない → 素攻撃 prior 継承 vs
  均等の A/B（§2.4）。長期的には箱化コーパスで再学習した policy が吸収
- **価値の盲点**: 配分済み盤面でも「カウンター強要の得」を value が読めない可能性
  → その場合は v50 乖離族と同根＝箱化の負けではなく評価の課題として切り分けて記録
