# 2026-10-22 WP `enc-audit`——ネットの入力の点検（公平化で意味が変わった特徴・隠れた情報を読んでいた特徴）

指示: `docs/search_efficiency_plan.md` §7.17（本線 `claude/cpu-spec-improvements-yw91jd` @ 93da7d38f・台帳 2+319）。
ブランチ `claude/enc-audit`。コードの変更は計器だけ（`tests/scripts/enc_fair_diff.py` と、その計器が使う測定専用の口
`Game.encode_world`〔`rust/opcg_engine/src/py_game.rs`〕）。符号化そのものは 1 bit も変えていない。

## 0. 結論（先に）

1. **符号化 v14 の特徴 287 本（scalars 127 列・場 16・card_idx 24 枠・トークン状態 5 ゾーン×22 列・関係 10 列に束ねたもの）のうち、公平化（`reveal=fair`）で値が変わるのは「自分の残り山札の集計」の 16 列だけ**
   （`deck_aggregate` 5・`deck_apex` 2・EXTRA の `deck_*` 9）。それ以外の 271 本は 20 局・2,632 判断点・世界 2 本のどこでも
   peek・fair・本物の盤面で **1 度も差が出なかった**（トークン状態 S・場・card_idx・相手の未見プールの集計・登場時スキャン・条件の旗を含む）。
2. **その 16 列は、本物の盤面では「伏せた自分のライフの中身」を漏らしていた**（山札の中身＝自分の残りの札 − 伏せたライフ）。
   peek の世界は自分の山札とライフを本物のまま使うので、**根の入力は peek＝本物で完全に一致**（全特徴で差 0）。
   fair では世界ごとに「山札＋伏せたライフ」を混ぜ直すので、16 列が世界ごとに揺れる（世界 0↔1 の非零割合が peek↔fair と同じ大きさ）。
3. **ただし価値の出力への効きは小さい**: 根の価値（手番側から見た勝ちの見込み・−1〜1）の差は peek↔fair で平均 0.006・90% 点 0.018・最大 0.13。
   **本物の入力のほうが勝敗をよく当てる、ということも無い**（勝敗への二乗誤差: 本物 0.6674・fair の世界平均 0.6666）＝今のネットは漏れを使えていない。
4. **訓練の入力はいまも本物の盤面で作っている**（`record_gen.py` の `game.encode(name)`）＝波 47（最初の公平な波）も 16 列は本物＝伏せたライフの漏れ入り。
   探索（serve・生成）は fair の世界で根も葉も符号化する＝**16 列だけ、訓練と探索で入力の作り方が違う**。
5. 提案（§3）: **v15 の第一案は「16 列を、分かっている分だけの確定的な値に置き換える」**（自分の残りの札〔山札＋伏せたライフ〕の集計を山札の枚数の割合で按分し、
   知っている札〔見て下に置いた札など〕は確定で数える）。列の数・位置・目盛りは今と同じにできる＝r13d の重みがそのまま読める。
   費用は Rust・Python の符号化 3 か所ずつ＋照合の更新。効きは小さい（価値で平均 0.005 程度の揺れが消える）ので、**r17 の訓練に合わせて入れるかどうか**はコーディネータとユーザの判断。

  `deck_counter` がほぼ 0 なのは、役割「カウンター」（カウンターイベント）が `synth_roles` の山にほとんど無いため。

## 3. 符号化 v15 の案（実装はしない）

### 3.1 案 A（推薦）: 自分の残り山札の 16 列を「分かっている分だけの確定的な値」に置き換える

**中身**: 自分の「残りの札」＝山札＋伏せたライフ（どちらも並び・分け方は自分に見えない）。そのうち自分が知っている札
（`known_by` に自分の bit＝見て山札の下へ置いた札など）は、どちらのゾーンにあるかが確定している。そこで 16 列を次で作る:

- 数える列（`counter_total`・`blockers`・`events`・`highcost_char`・役割 7・直した除去・バウンス）:
  **山札にあると分かっている札の数 ＋ 知らない札の数 × （山札の知らない枠の数 ÷ 知らない札の総数）**
  ＝「山札に何枚入っているか」の期待値。目盛り（/50・/10 の上限）は今と同じ。
- 密度（`counter_density`）: 上の期待値 ÷ 山札の枚数（山札の枚数は公開）。
- 頂点（`max_power`・`max_cost`）: 山札にあると分かっている札と知らない札の全部の最大（＝「残りの札のどこかに居る」頂点。伏せたライフに入っている確率は
  ライフ枚数 ÷ 残りの枚数＝序盤で約 1 割、その分だけ上振れする。期待値にしたければ「最大が山札側にある確率」で重みをつけるが、式が増えるので推薦は単純な最大）。

**根拠**:
- 本物の値は伏せたライフの中身を漏らしている（§2.2 の本物↔fair の差＝漏れの量）。fair の世界の値は偏りのない見本だが世界ごとに揺れる
  （世界 0↔1 で 16 列の平均 1/4〜2/3 が動く）。期待値に替えると**本物・peek・fair・どの世界でも同じ値**になり、漏れも揺れも同時に消える。
- 相手側はすでにこの形（`opp_pool_*`＝相手の残りの集合の集計）で、§2 で 1 度も揺れていない。自分の側だけが「山札だけ」を数えていた非対称を直すことになる。
- **列の数・位置・目盛りが変わらず、意味は「今の fair の世界の値の平均」**＝r13d の重みがそのまま読める（温スタートの pad も不要）。
  価値の出力の動きは「本物↔fair 2 本の平均」と同じ桁（平均 0.005・最大 0.07）と見込まれる。
- 訓練と探索で入力の作り方が揃う（今は訓練＝本物・探索＝fair の世界。§0 の 4）。

**費用**:
- Rust: `encode/scalars.rs`（`deck_aggregate`・`deck_apex`）と `encode/tokens.rs`（自デッキの役割 7＋2）の 3 か所。知っている札の判定は
  `known_by` を読むだけ（`determinize.rs::hidden_slots` と同じ判定）。キャッシュの鍵（card_id の並び）に「知らない枠の比」を足す必要がある。
  計算量は今と同じ桁（残りの札は山札より 5 枚前後多いだけ）。むしろ世界ごと・木の中で値が変わらない分キャッシュに当たりやすくなる。
- Python: `encoder.py`（`_deck_aggregate`・`_deck_apex`）と `n_rel_feat.py`（`_deck_roles`）の写し。Python の盤面は `known_by` を持たない
  （記録 v5 の `hidden` にも無い）ので、Python 側は「知っている札なし」として計算する＝Rust と一致させるには `known_by` を盤面へ渡す口が要る。
  `rs_encode_oracle.py` の照合はその口が入るまで「知っている札が無い盤面」に限る。
- 版: `ENC_VERSION` 15（形は v14 と同じ。npz の meta `enc_version` の照合を 14→15 で通す 1 行）。golden（監査・再生）は符号化を含まない＝作り直し不要の見込み
  （要確認）。`rs_enc_v14_probe.py` と同じ手順で「r13d を v15 で読んで手が大きく変わらない」ことを測る。
- 訓練データ: **記録は盤面を持たない**（scalars を保存しているだけ）ので、既存の波の 16 列を作り直すことはできない。
  v15 の符号化で生成した波（48 以降）から入れ替わる。価値の窓は「今と 1 つ前の生成役の波」（CLAUDE.md・2026-10-19）、方策の窓は今の era だけ
  なので、**2 波で全部が v15 の入力に入れ替わる**。混ざる間は「古い波の 16 列は本物＝漏れ入り」「新しい波は期待値」で、
  今の「訓練＝本物・探索＝fair の世界」より食い違いは小さい。
- 効き: §2.3 のとおり価値の揺れは平均 0.005 程度で、本物の入力が勝敗をよく当てているわけでもない＝**強さの上積みは小さいと見込む**
  （アリーナで差が出るとすれば、世界 2 本の平均で消しきれない序盤の揺れ〔平均 0.013〕の分）。主な価値は「入力の意味が隠れた情報に依らない」ことの保証。

### 3.2 案 B: 知っている札を入力に足す（相手の手札の知っている札・自分の山札の上の知っている札）

**中身**: 今の符号化は相手の手札を枚数でしか読まない（相手の手札に戻した自分の札・公開された札も読まない）。自分の山札の上を見て戻した札も読まない。
EXTRA の末尾に、相手の手札の知っている札のカウンター総量・枚数、自分の次のドローの札（知っていれば）のコスト・カウンター、などを足す。

**根拠**: fair の世界はこれらを位置ごと固定する＝探索は使っているが、ネットの入力には無い。
**費用と効き**: 列を足す（append-only・温スタートは新しい列 0 で恒等）。Rust・Python 両方に `known_by` を読む口が要る（案 A と共通）。
ただし頻度が低い（§2.5: 相手の手札に知っている札がある判断点 4.9%・平均 0.06 枚、自分の山札の上 4.7%・平均 0.09 枚）。**推薦しない**（費用に見合う効きの見込みが無い）。

### 3.3 案 C: 今の 16 列を削る

**中身**: 自分の残り山札の集計を入力から外す（列を 0 に固定する切り分け＝`--ablate` に `own_deck` を足す）。
**根拠**: 漏れと揺れは確実に消える。既存の波でも列を 0 にすれば訓練できる（盤面が要らない）＝**v15 の生成を待たずに試せる唯一の案**。
**費用と効き**: 訓練器に切り分けを 1 つ足すだけ。ただし「山に何が眠っているか」（v4／v9 で入れた理由: 掘りの価値・守り札の残り）が
ネットから見えなくなる。案 A はこの情報を漏れなしで残せるので、**案 C は案 A の対照（列が要るかどうかの測定）として**だけ意味がある。

### 3.4 ついでに見つけたもの（公平化とは別・判断は不要）

- **`field`（10×8）と card_idx のステージ 2 枠は NRel では読まれない**（`n_rel.py` の入力に無い）。記録・符号化で毎回作っている。
  外せば符号化がわずかに軽くなるが、記録の形（`record_gen.py`・訓練の読み込み）に触るので、別の作業で行うのがよい。
- **`EXTRA_COLS` に同じ名前の列が 2 本ある**: 役割 `big` の `opp_pool_big`（scalars 列 113）と、相手プールの脅威の `opp_pool_big`（列 115・7000 以上のキャラの枚数）。
  列の位置で読む限り害は無い（ネット・記録は位置で読む）が、名前で束ねる道具（本計器の初版）は片方を落とす。本計器は 2 本目を `opp_pool_big#2` として分けた。
  v15 で列名を直すなら `opp_pool_big_chars` などに改名する（append-only の契約は位置の契約なので、名前だけなら直せる）。
- **`deck_removal`／`opp_pool_removal`（v13）と `*_removal_fixed`（v14）はほぼ同じ量を 2 回読んでいる**（v13 はバウンスを数えない旧い数え方・
  append-only のため残している）。v15 で形を変えるなら旧い 2 列を外せるが、案 A は形を変えないことに価値があるので、外すのは見送りが妥当。

## 4. 判断を求める項目（コーディネータ・ユーザ向け）

1. **何を決めるか**: 自分の残り山札の集計 16 列を、伏せたライフの中身に依らない「期待値」に替える符号化（v15・案 A）を、r17 の訓練に合わせて入れるか。
2. **選択肢**:
   (a) 入れる——符号化の 3 か所×2 言語＋照合の更新。v15 の波（48 以降）から入れ替わり、2 波で訓練の入力が全部揃う。根の価値の揺れ（平均 0.005・序盤 0.013）が消え、入力が隠れた情報に依らなくなる。強さの上積みは小さい見込み。
   (b) 入れない——今のまま。訓練は本物（漏れ入り）・探索は fair の世界（揺れ入り）の食い違いが 16 列に残る。測った範囲では勝敗の当たりに差は無い（二乗誤差 0.6674 対 0.6666）。
   (c) 先に削る対照（案 C）だけ既存の波で訓練して測る——16 列が要るかどうかが分かる。要らなければ (a) も不要で、外すだけで済む。
3. **なぜこの問いが出てきたか**: 2026-10-21 に探索の世界の引き直しを公平（`fair`）に替えた（WP `rs-fair`）。その作業で、自分の残り山札の集計が
   「今までは本物の山札（伏せたライフの中身が漏れる）・今は世界ごとの混ぜ直した山札」に意味が変わることが分かり、他にも同じ種類の特徴が無いかを点検した（本 WP）。
   全 287 本を測って、該当はこの 16 列だけと分かった。
4. **推薦**: (a)。ただし急がない——効きは小さく、r17 の訓練の準備（符号化の版上げ・波 48 の生成）に合わせて入れるのが費用が最小。
   その前に (c) を 1 本回せるなら、16 列の要不要が先に分かる（要らなければ (a) の実装を省ける）。
5. **決めないとどうなるか**: 何も壊れない。訓練と探索の入力の作り方の食い違いが 16 列に残り、波 47 以降の「公平な波」も訓練の入力は本物のまま（漏れ入り）で作られ続ける。
6. **留保**: 期待値は「残りの札のどこにあるか分からない」ことの近似で、伏せたライフの枚数が多い序盤ほど本物から離れる（それが漏れを消すということ）。
   頂点（最大パワー・最大コスト）は単純な最大だと上振れする。Python の盤面は `known_by` を持たないので、Python 側の写しが Rust と一致するのは知っている札が無い盤面だけ（口を足すまで）。
