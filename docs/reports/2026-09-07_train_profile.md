# NRel 学習の時間・メモリ内訳（2026-09-07・計測 WP `train-profile`）

`docs/rust_engine_plan.md` §18.1。**全学習は回していない**——1 シャード・固定 200 バッチの部分計測で、
全体は「1 行あたり × 台帳の行数」で外挿する。学習コード（`tests/scripts/n_rel_train.py`）と
エンジンは無変更。計測用の複製は `tests/scripts/train_profile.py`、torch プロトタイプは
`tests/scripts/train_profile_torch.py`（どちらも新規・`n_rel_train` を import して同じ関数を呼ぶ）。

## 結論（先に）

**律速は backward（時間の 46〜54%）と、`--ablate rel` では捨てられる関係 R の再計算（29〜37%）。
両方とも 1 コアしか使っていない（4 コア中 25%）。効く手は 2 つだけで、データ形式とバッチサイズは効かない。**

| 手 | 実測 | 見込み倍率（1 エポック全体） |
|---|---|---|
| ① `--ablate rel` のとき `relations_batch` を呼ばない | value 1.46 倍・**損失は 200 バッチ全部でビット一致** | **1.44 倍** |
| ④ torch（CPU）化＋マルチコア | value ステップ 5.33 倍（4 スレッド・forward は numpy と 8.8e-7 一致） | ①と併せて **2.8 倍**（value だけ移植）／**7.7 倍**（policy も移植） |
| ③ float16/int16 の memmap | 常駐 2.08 倍圧縮・切り出しは 1 ステップの 0.17% | **時間には効かない**（メモリだけ効く） |
| ② バッチサイズ拡大 | 4 倍で 0.74 倍・16 倍で 0.64 倍＝**遅くなる** | **1 倍未満（やらない）** |

## 計測環境

Intel Xeon @2.80GHz・**4 コア**・16GB（cgroup）／Python 3.11.15・numpy 2.4.6（scipy-openblas
0.3.31 DYNAMIC_ARCH Haswell）・torch 2.14.0（CPU 実行）。`n_rel_train.py` は import 時に
`OMP_NUM_THREADS=1` 等を既定で立てるので、注記のない計測はすべて **BLAS 1 スレッド**（＝本番と同じ）。

入力は dump v2 の 1 シャード（`origin/claude/n28-w01` の `n28_records`・569 局・**81,871 行**・
方策点 46,325・候補行 643,652）。比例則の確認に `n28-w02`（960 局・136,631 行）を足した 2 本
（**218,502 行**）でも測った。

> **この計測機は過去の訓練機より遅い**。同じ式で過去の実績を再現すると a1 は 1.70 倍・r2 は 1.47 倍
> 大きく出る（後述「外挿」）。**比率（内訳・倍率）はそのまま読めるが、絶対秒は 0.6〜0.7 倍して読む**こと。
> 同じ計測を別の日に 3 回引いた value の 1 行あたり時間は 2.050／2.278／2.379 ms とばらついた（±8%）。

## 2. 学習ループの内訳（`train_profile.py loop`・200 バッチ）

`--ablate rel`・bs-v 256／bs-p 64・BLAS 1 スレッド。区間は本体と同じ式の複製に時計を挟んで測った。

| 区間 | value（2.050 ms/行） | policy（2.271 ms/点） |
|---|---|---|
| backward | **46.3%**（48.56 s） | **54.1%**（15.72 s） |
| **関係 R の再計算**（`relations_batch`） | **36.9%**（38.74 s） | **28.6%**（8.32 s） |
| forward | 15.9%（16.64 s） | 15.8%（4.58 s） |
| Adam 更新 | 0.8%（0.86 s） | 1.0%（0.30 s） |
| Python のバッチ切り出し | 0.1%（0.13 s） | 0.5%（0.15 s） |
| **CPU 使用率** | **1.00 コア／4（25%）** | **1.00 コア／4（25%）** |

**Python のバッチ切り出しは律速ではない（0.1〜0.5%）。Adam 更新も違う（1%）。**
時間は backward と、捨てられる R の再計算に消えている。

1 エポックの構成（1 シャード・holdout `seed%7==0` を除く）: value 訓練 70,306 行＝274 バッチ・
policy 訓練 39,762 点＝621 バッチ・合計 **234.0 秒**（value 61.4%／policy 38.6%）＝
**総行数あたり 2.86 ms**。

### 2b. 関係 R の再計算は捨てられている（`train_profile.py norel`）

`--ablate rel` では `NRelNet.mask_rel` が `relations_batch` の出力を `np.zeros_like` に置き換える。
つまり**計算した R は 1 バイトも使われない**。ゼロ配列を使い回した場合を 200 バッチで測った:

| | value 1 行あたり | 壁時計 |
|---|---|---|
| `relations_batch` を毎バッチ再計算（現状） | 2.379 ms | 121.78 s |
| ゼロ配列を使い回す | **1.624 ms** | 83.15 s |
| | **1.46 倍** | |

**損失は 200 バッチすべてで完全一致（最大絶対差 0.0）**＝挙動は変わらない。
policy 側は内訳の 28.6% から 1.40 倍相当（算術・未実測）。

### 2c. バッチサイズは大きくすると遅くなる（`train_profile.py bs`）

同じ行数（200×256 相当）で比較。

| 倍率 | bs-v / bs-p | value ms/行 | 1 行あたり速度比 | policy ms/点 | 速度比 |
|---|---|---|---|---|---|
| 1x | 256 / 64 | 2.278 | 1.00 | 2.326 | 1.00 |
| 4x | 1024 / 256 | 3.076 | **0.74** | 2.347 | 0.99 |
| 16x | 4096 / 1024 | 3.545 | **0.64** | 2.596 | 0.90 |

**大きくするほど遅い。** CPU 使用率は 1.00 コアのまま（BLAS 1 スレッドなので当然）で、
`keep` が `[B,16,16,101]` 等の中間テンソルを同時に持つためメモリ帯域で頭打ちになる
（16x は RSS 2.9GB）。value の backward 比率が 49%→64% に上がるのがその現れ。
**バッチサイズは高速化のレバーではない。**

## 3. データ形式の試算（`train_profile.py memmap`）

`V` の 4 配列を float16／int16 の `.npy` に書き出し、`mmap_mode="r"` で切り出した。

| 配列 | 現行 | memmap | |
|---|---|---|---|
| `sc` | float32 40.28 MB | float16 20.14 MB | |
| `ci` | int64 14.41 MB | **int16 3.60 MB** | 語彙 idx は int16 で足りる |
| `tok` | float32 144.09 MB | float16 72.05 MB | |
| `z` | float32 0.33 MB | float16 0.16 MB | |
| **合計** | **199.1 MB**（2,432 B/行） | **96.0 MB**（1,172 B/行） | **2.08 倍圧縮** |

切り出し速度（200 バッチ×256 行）:

| 読み方 | 1 行あたり | 1 ステップ（2.05 ms/行）に占める割合 |
|---|---|---|
| RAM 上（現行） | 1.25 µs | 0.06% |
| memmap・ランダム index | 3.48 µs | **0.17%** |
| memmap・ソート済み index | 3.76〜3.98 µs | 0.19% |

**memmap は現行の 2.8 倍遅いが、絶対値がステップの 0.2% なので実質タダ。**
float16 化による forward 出力の差は 1 バッチ（256 行）で**最大 1.07e-4・平均 1.53e-5**
（value の値域 [-0.95, -0.31]）＝v_mse 0.53 の水準に対して無視できる。

> **注意**: この切り出し計測は書き出した直後でページキャッシュが温かい（1 巡目 0.178 s と
> 2 巡目 0.179 s が同じ＝全部キャッシュ命中）。**全波 11GB 規模ではキャッシュに乗り切らず、
> ランダム index の memmap は実ディスク I/O になる**。時間ではなくメモリのための手段と考えること。

## 4. PyTorch（CPU）のプロトタイプ（`train_profile_torch.py`）

`NRelNet` の value 経路（`card_table`／`tokens_forward`／`body`／value ヘッド）を torch で同じ式に
書き、`n1_results/nrel_a1.npz` の重みを読んで突き合わせた。backward は autograd・更新は
`torch.optim.Adam`（手書き backward の複製はしていない＝プロトタイプ）。

**forward 一致（1 バッチ 256 行）: 最大絶対差 8.79e-7・平均 1.19e-7 ＝ 1e-5 で一致（合格）。**

同じ 200 バッチ（bs 256）の時間。**両者ともバッチは事前に用意してあり、`relations_batch` と
切り出しは計測に含まない**（＝①を適用したあとの土俵での比較）:

| | ms/行 | CPU 使用 | numpy 比 |
|---|---|---|---|
| numpy・1 スレッド（**本番と同じ設定**） | 1.406 | 1.00 コア | 1.00x |
| torch・1 スレッド | 0.616 | 1.00 コア | **2.28x** |
| torch・2 スレッド | 0.392 | 1.99 コア | **3.59x** |
| torch・4 スレッド（全コア） | **0.264** | 3.95 コア | **5.33x** |

**1 スレッド同士でも 2.28 倍**（＝手書き numpy の中間配列の作り方が非効率）、**スレッドを増やすと
ほぼ線形**（4 スレッドで実効 3.95 コア）。numpy 側は BLAS を 4 スレッドにしても伸びない（次表）。

**対照: numpy の BLAS スレッドを 4 に上げても速くならない**（`OMP_NUM_THREADS=4` で同じ 200 バッチ）:

| | ms/行 | CPU 使用 |
|---|---|---|
| numpy・BLAS 1 スレッド | 1.406 | 1.00 コア |
| numpy・BLAS 4 スレッド | **1.517（むしろ 8% 遅い）** | 1.74 コア |
| torch・4 スレッド（同条件） | 0.295 | 3.93 コア |

1.74 コアを使いながら 1 スレッドより遅い＝**行列積が小さすぎてスレッド分割のオーバーヘッドが勝つ**。
`n_rel_train.py` が import 時に `OMP_NUM_THREADS=1` を立てているのは正しい。
**「環境変数でコアを増やす」は手にならない。マルチコアを取るには torch 化が要る。**

## 5. 全波への外挿

外挿は **「1 行あたり × 台帳の行数」**。1 エポックは 2 項の和で組む（holdout 1/7 を除く）:

```
epoch_sec = (6/7) × ( value行数 × 2.050ms + 方策点数 × 2.271ms )
load_sec  = 行数 × 6.99e-5 s      RSS = 行数 × 2,845 B
```

台帳（`docs/n_loop_ops.md` §6）の行数を入れる。方策点は本計測の比（1 行あたり 0.566 点）を使う
（r2 だけは実績の点数が残っているのでそれを使う）。

| 規模 | 行数 | 方策点 | 読み込み | RSS | 1 エポック（当機） | 実績 | 当機/実績 |
|---|---|---|---|---|---|---|---|
| a1 相当（波23＋24） | 2,164,053 | 1,224,484 | 151 s | 6.2 GB | 6,186 s（1.72 h） | 3,630 s/ep（7,417 s÷2ep） | 1.70 |
| r2 実績（波25〜26 π＋波23〜26 z） | 4,248,000 | 1,183,000 | 297 s | 12.1 GB | 9,767 s（2.71 h） | 6,540 s/ep（6,837 s−load） | 1.47 |
| 波25〜28 相当（4 波・r2b の規模） | 4,480,000 | 2,534,000 | 313 s | 12.7 GB | 12,805 s（3.56 h） | — | — |

**当機は過去の訓練機の 1.47〜1.70 倍遅い**（コンテナの CPU が違う）。実機の見込みは上の値を
0.59〜0.68 倍して読む。RSS の外挿は cgroup 14GB に対し**波 4 本＝12.7 GB でぎりぎり**で、
「古い波から落として上限内に収める」運用（CLAUDE.md・ユーザ決定 2026-09-01）の実測裏付けになる。

### どの手で何倍になるか（1 エポック・a1 相当 2,164,053 行で計算）

| 段 | value ms/行 | policy ms/点 | 1 エポック | 現状比 |
|---|---|---|---|---|
| 現状 | 2.050 | 2.271 | 6,186 s | 1.00x |
| ① R 省略（value のみ・実測） | 1.404 | 2.271 | 4,980 s | 1.24x |
| ① R 省略（policy も・算術） | 1.404 | 1.621 | 4,298 s | **1.44x** |
| ①＋④ torch 4 スレッド（value のみ移植） | 0.263 | 1.621 | 2,189 s | **2.83x** |
| ①＋④（policy も移植・**推定**） | 0.263 | 0.304 | 806 s | **7.67x** |

**①は今日そのまま入れられる**（`--ablate rel` のときだけ `relations_batch` を呼ばない・損失ビット一致）。
**④は policy ヘッドまで移植して初めて 7〜8 倍になる**——value だけだと policy が残って 2.8 倍で頭打ち
（policy が現在の 1 エポックの 38.6% を占めるため）。上表の最下段だけは実測でなく推定である。

## 6. §18.2 への申し送り

1. **まず①**。`--ablate rel` は現行の生成役 a1・訓練 r2/r2b の既定なので、**分岐を 1 本足すだけで
   1.44 倍**。損失がビット一致するので判定への影響もない。R を使う設計に戻すときのために
   `relations_batch` 自体は残す。
2. **次に④**。numpy の手書き backward を torch に置き換える。**1 スレッドでも 2.28 倍**あるので
   マルチコアが取れない環境でも損しない。value と policy の**両方**を移植して初めて 7〜8 倍。
   forward が 1e-5 で一致することは本 WP で示した（8.79e-7）ので、移植の受け入れは
   「forward 一致＋勾配一致＋同じ教材で val v_mse が一致」で機械的に組める。
3. **③は時間ではなくメモリの手**。float16／int16 で常駐 2.08 倍圧縮＝**同じ 14GB に 2 倍の波が載る**。
   Rust 生成が最初からこの形（`tok` float16・`ci` int16）で memmap を書けば、読み込み
   6.99e-5 s/行（全波 300 秒）も消える。切り出しコストはステップの 0.2% なので無視してよいが、
   全波規模ではページキャッシュに乗らない点に注意。
4. **②はやらない**。バッチサイズ拡大は 4 倍で 0.74 倍・16 倍で 0.64 倍と**逆効果**。

数字の一次情報は同じ内容の `RESULT.json`（WP ブランチ直下。本線では `docs/reports/2026-09-07_train_profile.RESULT.json` に移した）にある。
