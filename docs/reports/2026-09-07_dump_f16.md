# dump v3（float16/int16）と memmap 読み（2026-09-07・WP `dump-f16`）

`docs/rust_engine_plan.md` §18.5。`docs/reports/2026-09-07_train_profile.md` §3 の試算
（float16/int16 で常駐 2.08 倍圧縮・切り出しはステップの 0.2%・fp16 の forward 差 1.07e-4）を
本番に入れた。**教材の生成側を dump v3 に切り替え、学習側は V を RAM に載せず memmap で読む。**

- 生成 `opcg_sim/loop/record_gen.py`: **dump v3 が既定**（`tokens`/`scalars` を float16・
  `card_idx` を int16 で書く＝float32/int64 を cast しただけ。`enc_version` は 13 のまま・
  `dump_version=3`）。v1／v2 を書く経路は無い（`--dump-v2` は受けるだけの廃止旗）。
- 読み `opcg_sim/learned/train/dump_io.py`（新規）: `load_dump` が今までの `load_dump_v2` と
  同じ V/P/C を返す。V の `tok`/`sc`/`ci`/`z` は **波ごとの `.npy`（float16/float16/int16/float16）を
  `mmap_mode="r"` で開いた memmap**。pack はシャードの一覧・サイズ・mtime で鍵付けし 1 回だけ作る。
  **v2 の npz（float32/int64）も同じ関数で読める**（pack を書くときに cast する）。
  `n_rel_train.load_dump_v2` は `load_dump` を呼ぶ薄い互換。
- 訓練 `n_rel_train.py`／評価帯 `n_rel_band.py` は `load_dump` に差し替え、**切り出した後で
  float32／int64 へ上げる**（`dump_io.rows_f32`）。**切り出しの形（`V["tok"][bi]`）は変えていない**。

## 計測環境

Intel Xeon @2.10GHz・**4 コア**・15GB／Python 3.11.15・numpy 2.4.6・torch 2.14.0（CPU 実行）。
BLAS は 1 スレッド（`n_rel_train` の既定）、torch は 4 スレッド。入力は
`origin/claude/n28-w01`（57 シャード・**81,871 行**・方策点 46,325）と `n28-w02`（96 シャード・
136,631 行）＝2 波で **218,502 行**。**この計測機は §18.1 の計測機（2.80GHz）より遅い**ので、
絶対秒は横に比べるのではなく本報告内の v2 対 v3 で読むこと。

## a. 生成: v3 は cast しただけ（`dump_f16_check.py gen`）

同じ seed（910001〜910006・sims 16・6 局とも決着）を **v3** と **`DT_V3` を外した v2**（float32/
int64）の 2 通りで生成し、646 行を突き合わせた。

| 見たもの | 結果 |
|---|---|
| `tokens` | `v3 == v2.astype(float16)` が**全行ビット一致**。float32 へ戻したときの最大絶対差 **3.906e-4** |
| `scalars` | 同上・最大絶対差 **3.906e-4** |
| `card_idx` | **完全一致**（int16 → int64 で元の値。値域は語彙数 ≒2,651 ≪ 32,767） |
| 他の列（`z`・`who`・`kind`・`turn`・`step`・`seed`・`pol_*`・`sig`） | **すべてビット一致**（v3 で触っていない） |

fp16 で表せる値は等しく、それ以外は最近接（差は値の相対 2^-11）。ラチェットは
`tests/test_n_record_v3.py`。

1 行あたりのバイト（**圧縮前**・生成した行そのもの）:

| | v2 | v3 | 比 |
|---|---|---|---|
| 行の全列（`field` 等を含む） | 2,847 B | **1,577 B** | 0.554 |
| 学習が常駐させる V（`tok`+`sc`+`ci`+`z`） | 2,432 B | **1,176 B** | **0.484** |

> `field`（float32・320 B/行）は v3 でも float32 のまま残した（指示の対象は tokens/scalars/
> card_idx の 3 本）。NRel も N系 c も `field` を読んでいないので、更に落とす余地がある。

**npz（`savez_compressed`）のディスク上のサイズは 199.6 → 183.0 B/行＝0.917 にしかならない**
（w01 の 6 シャード 8,539 行で実測）。tokens はゼロが多く zlib が既に潰しているため。
**v3 の利得はディスクではなく常駐（RAM）にある。**

## b. RSS: 2 波の load 後の増分（`dump_f16_check.py rss`）

「v2 を float32/int64 で RAM に載せる旧実装」（本線 0633d0d の `load_dump_v2` の写し＝
`load_dump_v2_ram`）と「v3 memmap」を同じプロセスで順に回して RSS 増分を測った。
pack は事前に作ってある（pack を作る回の山は初回だけの一時的なもので常駐ではない）。

| | 行数 | v2（RAM） | v3（memmap） | 比 |
|---|---|---|---|---|
| 1 波（w01） | 81,871 | **0.228 GB** | **0.000 GB**（−0.13 MB） | ≈0 |
| **2 波（w01+w02）** | 218,502 | **0.524 GB** | **0.035 GB** | **0.066** |
| V の実バイト（1 行あたり） | | 2,432 B | 1,176 B | 0.484 |
| load 壁時計（2 波） | | 8.64 s | **5.89 s** | 0.68 |

**受け入れ（55% 以下）に対して 6.6%**。memmap なので V は RSS にほぼ乗らず、残る 35 MB は
P/C（39 MB＝方策点と候補・従来どおり RAM）と読みの一時領域。load 自体も速くなった
（pack があれば `tok`/`sc` を展開しないため。P/C を作るのに npz の `pol_*` は読む）。

## c. 学習 1 エポック（`dump_f16_check.py train`）

w01（81,871 行・方策点 46,325）・warm-start `nrel_a1.npz`・`--ablate rel`・backend torch
（4 スレッド）・bs-v 256／bs-p 64・895 ステップ。**同じ seed・同じバッチ順**。

| | v2（float32・RAM） | v3（memmap） | 差 |
|---|---|---|---|
| val **v_mse** | 0.684204 | 0.684833 | **+0.092%**（受け入れ ≤1%） |
| val v_sign | 0.75547 | 0.75417 | −0.0013 |
| val pi_top1 | 0.60375 | 0.59950 | −0.0043 |
| train mse / ce | 0.46002 / 1.71489 | 0.45943 / 1.71470 | — |
| **1 エポック（学習ループのみ）** | 28.05 s | **29.33 s** | **+4.6%**（受け入れ <10%） |
| 読み込み＋評価を含む全体 | 37.8 s | **34.5 s** | −8.7% |

学習ループは +4.6% 遅い（memmap の切り出しが RAM の 2.8 倍かかるぶん＝§18.1 §3 の試算どおり
ステップの 0.2% 水準）が、読み込みが速くなるので**通しでは速い**。

## d. 全波規模の注意（ページキャッシュに乗らない）

この計測の 2 波（218,502 行・pack 259 MB）は**丸ごとページキャッシュに乗る**。切り出しが
「RAM の 2.8 倍」で済んでいるのはそのためで、**全波規模ではそうならない**:

- 台帳の 1 波は 8 シャード×960 局 ≒ 100 万行＝pack **1.18 GB/波**。z 窓を 10 波取れば **11.8 GB** で、
  cgroup 14GB のページキャッシュには収まらない（訓練プロセス自身・P/C・torch も同じ RAM を使う）。
- そうなるとランダム index の memmap は**実ディスク I/O** になり、1 ステップの切り出しは
  0.2% では済まない。**v3+memmap は時間ではなくメモリのための手段**と考えること
  （RAM に載らなくなって OOM で止まる、が無くなるのが利得）。
- 波を増やすときは pack の置き場所（`--cache-dir`／`$OPCG_DUMP_CACHE`・既定
  `~/.cache/opcg/dump_pack`）**のディスク残量**を先に見ること（1.18 GB/波）。
  古い波の pack は消してよい（次に読むときに作り直す）。
- 切り出しをソートしても速くならない（§18.1 §3 で実測・むしろ僅かに遅い）ので、
  バッチ順を触る最適化は要らない。

## 副作用として測ったもの: fp16 の tokens から関係 R を再計算すると境界が反転する

`docs/n_attention_plan.md` は P1 の時点で「tokens は float32（float16 は境界で反転・実測）」と
書いている。**その反転は今も起きる**ので、量を測って残す（w01 シャード 0 の先頭 2,000 行・
`relations_batch` を float32 と fp16 丸めの tokens で回した差）:

| チャネル | 差のある要素の割合 | 最大絶対差 |
|---|---|---|
| `atk_margin` | 2.74% | 5.86e-4 |
| `ko_gap` | 0.12% | 3.91e-4 |
| `cost_gap` | 1.40% | 1.95e-4 |
| `red_amount` | 0% | 0 |
| **`feasible`（真偽）** | **0.050%**（137,568 対中 69） | **1.0（反転）** |

連続値は丸めそのもの（≤5.9e-4）。**真偽が反転するのは (自枠×相手枠) の 0.05%** で、
「境界ちょうどの組はどちらに転ぶか分からない」という性質は変わらない。

- **serve は影響を受けない**（実対局は生の float32 の符号化から R を計算する。dump は通らない）。
- **現行の N 系の学習線も影響を受けない**（a1／r2 は `--ablate rel`＝R を計算せず 0 を渡す）。
- **R を使う訓練を再開するときはここを承知して使うこと**。教師そのものが 0.05% だけ違う
  盤面になる（学習が壊れる水準ではないが、「dump から再計算した R は serve の R と
  ビット一致する」とはもう言えない）。

## 残り（やっていないこと）

- **既存の波（v2）は変換していない**。`load_dump` が読めるので変換は要らない（pack は同じ形に
  なる）。ディスクを空けたいときだけ再保存を考える（npz は 8% しか縮まない＝割に合わない）。
- `field` を float16 に落とせば行あたり更に 160 B 減る（誰も読んでいない列）。
- pack に P/C（方策点・候補）は入れていない＝毎回 npz の `pol_*` を読み直す（2 波で 5.9 s の
  ほとんどがこれ・`pol_sig` の JSON を 1 本ずつ解く）。ここを pack に入れると load は更に縮むが、
  `vocab` 依存の列（`cid`/`tcid`）があるので鍵に語彙を混ぜる必要がある。
