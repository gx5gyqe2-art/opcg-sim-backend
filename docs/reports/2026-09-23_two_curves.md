# T137a: 2 本の曲線の器——理論の累積 `G(t)` と棋譜の累積 `R(t)`（2026-09-23）

ユーザ提案「打った手を何かの数字にして、それを累積スコアを時系列でグラフのように表せるよね？
…打った手による近似式と棋譜のグラフが一致したところをゴールにするのが理論の完成」の器化。
T18 の前段のタスク分解（塊 A）の最初の一歩。

**器**: `tests/scripts/two_curves.py`（新規）・`tests/test_two_curves.py`（新規・11 本）。
**記録**: 実 = `w41`（300 局）／合成 = `w39 + w42`（900 局）。

---

## 0. 結論（先に書く）

1. **式（新定数ゼロ・既存の価格式の再利用のみ）**:
   * **`G(t)`** = その席が自席ターン `t` までに選んだ全ての決定（`TURN_END` 以外）の理論値
     （`theory_order.score_candidate`）を、帳簿の規約（`theory_bridge.ledger_value`・T58 の
     `exercise` 変換＋T85 の付与ゼロ化）で読み直したものの累積。
   * **`R(t)`** = 同じ `t` までに、その席が相手に実際に与えた損害
     （`attack_response.parts`／`parts_mirror` の `opp_life + opp_hand + opp_body`・
     `crossing_bridge.harm_of` と同じ式・T113 と同じブラケット規約）の累積。
2. **配線の検算が両記録・実データで完全一致した**——`crossing_bridge.py` のコードを 1 行も
   呼ばずに独立に書いた `R(t)` の終点（勝った席の合計）の平均が、`crossing_bridge.collect()` が
   別に計算する `F_end_mean` と**小数点以下まで一致**:

   | | 実（300 局・600 席） | 合成（900 局・1800 席） |
   |---|---|---|
   | 本器の `winner_final_r_mean` | **1.0399** | **0.9256** |
   | `crossing_bridge` の `F_end_mean` | **1.0399** | **0.9256** |
   | 差 | **0.0** | **0.0** |

   **2 つの別々に書いた実装が同じ答えに収束した**——`R(t)` の式・ブラケット規約は正しく移植できている。
3. **`G(t)` には既知の簡略化がある**——`score_candidate` の探す能力（`PLAY` の一部）の価格付けは
   デッキ依存の計画価格（`search_ctx`・T68）を必要とするが、**本器はそれを渡さない**（デッキ非依存の
   既定 `sel(k)` に落ちる・`score_candidate` は `ctx.get("search_ctx")` で欠落を許容するのでクラッシュは
   しない）。**探す能力を持つ `PLAY` の価格だけやや粗い**——影響の大きさは T137b で測る。
4. **粗い水準感**（実／合成）: `end_g_mean` 1.5488／1.1238・`end_r_mean` 0.9626／0.8553——
   **理論の累積は実現の累積よりやや大きい**（比 1.61／1.31）。方向・大きさとも T89（`A` の過大＝
   1.26／1.20 倍）と整合的で、驚きは無い。**細かい形（増分の一致・型別の内訳・決着の印）は T137b/c/d**。

## 1. 器の設計

`two_curves_for_game` — 1 局ぶんの `(局×席の累積系列, 勝者)` を返す。決定行を順に読み、
**`G`（理論値）は `theory_order.score_candidate` ＋ `theory_bridge.ledger_value`（T58）＋ `move_family`
による付与ゼロ化（T85）**、**`R`（実現）は `attack_response.parts`／`parts_mirror`（T113 のブラケット規約）**
で積む。両方とも既存の価格式・既存のブラケット規約を**そのまま呼ぶだけ**（式は 1 行も新設していない）。

`collect` — 記録全体を読み、局×席ごとの終点・勝った席の `R` 終点の平均などを集計する。
`--dump` で局×席ごとの `(turns, g, r)` 系列を JSON に書き出す（T137b/c/d の材料）。

`verify_against_crossing_bridge` — `crossing_bridge.collect()`＋`summarise()` を呼び、**独立に書いた
`R` の終点**と `crossing_bridge` 自身の `F_end_mean` を突き合わせる（§0-2）。

---

## 2. 上手くいったこと／いかなかったこと

**上手くいった**:
* **配線の検算を「同じコードの使い回し」ではなく「独立実装の収束」にした**——`crossing_bridge` の
  `harm`／ブラケットのコードは 1 行も import せず、`attack_response.parts`／`parts_mirror` という
  **より下の層の共通部品**だけを再利用して独立に書き直した。だから一致は「配線を間違えていない」
  ことの本物の証拠になる（同じ関数を 2 回呼んでいるだけなら一致は当然で、証拠にならない）。
* **20 局→300 局→900 局と段階的に確かめた**——小さいサンプルで一致を見てから全量に進んだので、
  デバッグの往復が短く済んだ。
* **`collect` の戻り値の形を早合点しなかった**——`crossing_bridge.collect()` が辞書ではなく
  5-tuple を返すことに実装時に気付き、`main()` の実際の使い方を読んでから直した
  （最初 `.get()` で呼んで `AttributeError` を踏んだ・自己訂正して原因を特定）。

**いかなかった／自己批判**:
* **`G(t)` に `search_ctx` を渡さない簡略化を先に決めてから測った**——`score_candidate` が
  欠落を許容することを確認したうえでの判断だが、**探す能力の価格がどれくらい粗くなるかを
  まだ測っていない**。T137b で型別に見るまでは「粗い」がどれだけ粗いか分からない。
* **`G(t)` 側には `R(t)` のような独立の配線検算が無い**——比べる相手（同じ量を別に計算している器）が
  無いため。**`theory_bridge.collect()` 自身の `g_row`（信号は同じだが符号付き・結合形）との
  部分的な突き合わせ**が次に測れる候補だが、本 T の範囲では見送った。
