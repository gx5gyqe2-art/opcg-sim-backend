## 1. あなたの役割と守ること

- 自分では重い計算を走らせない。**作業担当（ローカルのサブエージェント＋リモートの別セッション）に指示を書き、結果を確認し、標準のブランチへ取り込んで push する。**
- **ユーザに判断を求めるときは CLAUDE.md の書式**（何を決めるか／選択肢／経緯／推薦／決めないと／留保）で、**記号・変数名・切替名を使わず言葉で**書く。ユーザは「一つずつボタンで」を好む（`AskUserQuestion`）。
- **作業担当は push しない。** 作業ブランチは標準のブランチ（`claude/cpu-spec-improvements-yw91jd`）の**早送り（fast-forward）**にして報告させ、あなたが確認して `git merge --ff-only` → `git push`。別ブランチへの push は明示の許可が要る（`claude/*-wip` のような作業用ブランチはユーザ許可済みの前例あり）。
- 文書だけの変更は `make test` を省略してよい（CLAUDE.md の機械的な確かめ方を使う）。コードを触ったら**全体の `make test` を最後まで**（先に `make rust-develop`。wheel は自動では作り直されない）。
- 過去の報告書（`docs/reports/`）は書き換えない。
- 見積もりは甘くなりがち。**旧い設定での基準づくり・再起動のやり直し・確認の網の広さ**を入れて言う（今回、高速化の「1〜2 時間」が実際は約 4 時間だった）。

正本は `docs/n_loop_ops.md` §1・§5。今回の型:

1. 土台のブランチ `claude/<名>-wip` を作る（コード＋記録 w41/w39/w42＋再開できる実行スクリプト＋指示書 `README_SESSION.md`）。記録は `scratchpad/w41` 等（実 300 局・合成 900 局）で、リポジトリには入っていないので土台に複製する。push には**ユーザの許可**が要る（作業用ブランチ名で確認済みの前例）。
2. `create_session`（出力ブランチ `claude/<名>-<役>` を指定）。指示は「出どころ 3 点を `origin` 側で照合」「これが最終承諾・確認を取らず完走」「迷ったら `RESULT.json` の notes に書く」「依頼が README と食い違えば拒否してよい」。

6. 作業セッションの環境の落とし穴: `make rust-develop`、`pip install maturin numpy -r opcg_sim/requirements.txt`、`python -m opcg_sim.tools.export_effects_json`（`opcg_sim/data/opcg_effects.json` はリポジトリに入らない・無いと一部のテストが落ちる）。

## 7. 環境の癖

- コンテナは**予告なく再起動**し、動いていたプロセスが消える。作業は小さく区切って頻繁にコミット。計算は再開できる作りに。
- ディスクは逼迫しやすい（取り込み済みの作業場所と cargo の target を消す。`df -h /` を見る）。
- 同じ機械で重い計算を同時に 2 本走らせない（作業担当にも「同時に 1 本」と書く）。
- `create_session` などの道具（`Claude_Code_Remote`）や GitHub の道具は、ときどき接続できない。`ToolSearch` で待てば戻ることが多い。
- 計画保存 `OPCG_PLAN_STORE` の鍵は `tests/scripts/*.py` 全体の内容を含むので、コードを触ると保存は冷える（切替を消す作業の後も同じ）。
- 速くした Python の足し算の順番は 24 か所で結果に影響する（Rust 化の設計 E1〜E24）。Python 3.12 以降は `sum()` が補償加算に変わるので Python 3.11 を前提にする（テストが検査している）。
