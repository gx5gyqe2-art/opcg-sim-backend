# 2026-10-22 WP `enc-v15`——自分の残り山札の集計を「分かっている分だけの期待値」に置き換える

指示: `docs/search_efficiency_plan.md` §7.19（本線 `claude/cpu-spec-improvements-yw91jd` @ 25a51f28a・台帳 2+322）。
根拠: `docs/reports/2026-10-22_enc_audit.md` §2・§3.1（案 A）。ブランチ `claude/enc-v15`。

## 0. 結論（先に）

1. **符号化 v15 を入れた**（Rust・Python の両方・`ENC_VERSION` 15）。自分の残り山札の集計 16 列
   （`deck_aggregate` 5・`deck_apex` 2・EXTRA の自デッキの役割 7・直した除去・バウンス）を、自分の「残りの札」
   （山札＋伏せたライフ）から作る「山札に何枚入っているか」の**期待値**にした。列の数・位置・目盛りは v14 と同じ
   ＝r13d の重みをそのまま（pad もせず）読む。
2. **本物・peek・fair・どの世界でも同じ値**を実測で確かめた（`enc_fair_diff.py`・20 局・出荷の設定 2,559 判断点／
   160 回 2,622 判断点）: **287 本の特徴の全部で、peek↔fair・本物↔peek・本物↔fair・fair の世界 0↔1 の差が 0**。
   知っている札の扱いの近似で差が残った判断点は **0 件**。根の価値の出力も 4 つの組すべてで差 0（ビット一致）。
3. **手の変わり方は小さい**: r13d を v15 と v14 で読み比べると、候補が 2 つ以上ある判断点の **97.7%（433/443）**・
   全判断点の 98.9%（1,052/1,064）で同じ手（1,280 回・世界 1 本・予算なし・8 局）。
4. **手元アリーナ 40 ペア**（候補 v15・基準 v14・両席 r13d・1,280 回・予算なし・世界 1 本・synth_roles・seed base 1680000）:
   決着 39 ペアで勝率 0.449（95% CI 0.330–0.567・−35.8 Elo）・**void 1 ペア（2.5%）**。CI は予告の ±10 を含み、
   40 ペアでは何も言えない。void 率が 2% を超えたので**判定は出さない**（CLAUDE.md）。void の原因は符号化ではなく
   **エンジンの誘発の順序の欠陥**（§4）——v15 の打ち筋がその盤面に入っただけ（同じ seed を両席 v15 で打つと再現・両席 v14 では入らない）。
5. ゲート: `make test` 緑（cargo 594 passed／pytest 854 passed・13 skipped）・`make audit-cross` void 0（120 ペア）。
   golden: 監査（3,386 件）と random 150 局は**不変**、a1 50 局は作り直した（16 局が同一・34 局が分岐・勝者が変わったのは 9 局）。

## 1. 仕様（実装したもの）

自分の「残りの札」＝山札＋伏せたライフ（並び・分け方は自分に見えない）。`known_by` に自分の bit がある札（知っている札）は、
どちらにあるかが確定している（`fair` は位置ごと固定する）。

- **数える列**（`counter_total`・`counter_density` の分子・`blockers`・`events`・`highcost_char`・役割 7・直した除去・バウンス）:
  `山札にあると分かっている札の和 ＋ 知らない札の和 × 山札の知らない枠の数 ÷ 知らない札の総数`。
  伏せたライフにあると分かっている札・表向きのライフは山札に入らない（数えない）。
- **密度**（`counter_density`）: 上の期待値 ÷ 山札の枚数（公開）。
- **頂点**（`max_power`・`max_cost`）: 山札にあると分かっている札と知らない札の全部の最大（報告 §3.1 の推薦どおり単純な最大）。
- **目盛り**: v14 と同じ（/50・/10 の上限・/2000 等）。

世界に依らない理由: `fair` は知らない札を知らない枠の中でだけ混ぜ直す＝知らない札の集合と枠の数は世界に依らない。
足し込むのは整数（カウンター値・枚数・役割の 0/1）だけ＝足す順に依らず厳密で、割るのは最後の 1 回＝**ビットまで一致**する。

| 場所 | 変更 |

**Python は版で分けない**: NRel の Python 側は `E.encode(version=12)`＋`encode_rel` で組むので、版の引数では 16 列を切り替えられない。
Rust も版で分けない（測定用の `deck_v14` だけ）＝**16 列は常に v15 の作り**（c 系〔`n_eff`・v12〕の Python 符号化も同じ関数を通る）。

**キャッシュの鍵**（報告 §3.1 の注意）: Rust には山札の中身を鍵にするキャッシュが無かった（幹のキャッシュの鍵は scalars のビット列そのもの＝自動で正しい）。
鍵の直しが要ったのは Python の `_DECK_ROLES_CACHE` だけで、鍵に「知っている札の並び・知らない札の並び・山札の知らない枠の数」を入れた。

**Python の知っている札の口**: カードの `known_by`（Rust と同じビット・P1=1・P2=2）と席の `know_bit` を読む。今の Python の盤面はどちらも持たない
＝「知っている札なし」で計算する。Python と Rust の符号化の照合（`rs_encode_oracle.py`）は `legacy/` に退避済みで今のスイートには無い
（v14 以降の照合は `test_enc_v14.py` の forward の一致だけ）＝照合を「知っている札が無い盤面」に限る件数は 0 件（回す照合が無い）。

## 3. 訓練データへの影響（コーディネータ向け）

- 記録は盤面を持たないので、既存の波（47 まで）の 16 列は v14 の作り（本物＝伏せたライフの漏れ入り）のまま。v15 の生成（波 48 以降）から入れ替わる。
  価値の窓（今と 1 つ前の生成役の波）・方策の窓（今の era）なので **2 波で全部が v15 の入力**になる（報告 enc-audit §3.1）。
- 形は v14 と同じ＝`dump_io` はそのまま混ぜて読む（`enc_version` は meta に 15 と書くだけで、読み手は版を見ない）。

## 4. void の原因（エンジンの誘発の順序の欠陥・本 WP では直さない）

seed 1680032（OP17-079 ルフィ〔エルバフ〕 vs OP06-080 モリア）の a 局（p1＝候補）で、ターン 13 に p1 の `RESOLVE_EFFECT_SELECTION` が
120 手以上続いて上限手数（400）に達する。

- 中身: ブロギー（OP17-092）【登場時】「トラッシュからドリーを登場させる。**その後、このターン中、キャラカードを登場できない**」→
  場が 6 体になり押し出し（どれをトラッシュするか）の対話 → 打ち手は**今出したドリー**をトラッシュ → ドリー（OP17-085）の【登場時】
  「トラッシュからブロギーを登場させる。その後…」→ 押し出しで今出したブロギーをトラッシュ → … の無限の往復。
- 原因: **待ち行列に積んだ【登場時】が、押し出しの対話が終わった時点で親の効果の残り（「その後、登場できない」）より先に解決される**。
  正しい順序なら親の効果（制限の付与まで）を解決し切ってから子の【登場時】を解決し、子の登場は制限で止まる。
  あわせて、効果による登場（`effects/actions/flow.rs::play_card`）は `CANNOT_PLAY_CHARACTER` を見ていない（手札からの登場だけが見る）。
  後者だけを直す試し（制限中はキャラの効果登場をしない）では**止まらなかった**（制限が付く前に子が解決されるため）＝本体は前者。
- 符号化とは無関係: 同じ seed を**両席 v15** で打つと再現・**両席 v14** では別の打ち筋になってこの盤面に入らない。カード DB の効果の解析は正しい
  （`opcg_effects.json` で PLAY_CARD → RULE_PROCESSING `CANNOT_PLAY_CHARACTER` の順の Sequence）。
- 直すとルールの挙動が変わり golden（監査・再生）が動く＝本 WP（golden 不変が条件）の範囲外。別の WP を提案する（RESULT.json の notes）。

### 判断を求める項目

1. **何を決めるか**: 誘発の順序の欠陥（押し出しの対話の後、親の効果の残りより先に子の【登場時】が解決される）を直す作業を、
   v15 の合流・波 48 の生成の前に入れるか。
2. **選択肢**:
   (a) 先に直す——ルールの作業 1 本（誘発の待ち行列を「親の効果を解決し切った後」に消化する・効果による登場も「登場できない」を見る）。golden の作り直しとレビューが要る。
   今回の void（40 ペアで 1・2.5%）は消える見込み。
   (b) 直さずに v15 を合流——今回の void はこの 1 組のカード（ブロギー／ドリー＝OP17 のエルバフ）でだけ確認。生成・アリーナで同じ盤面に入れば void
   （生成では上限手数で切れた局として捨てられる）。頻度は 40 ペアで 1 ペア、120 ペアの交差監査（synth・32 回）では 0。
   (c) v15 は合流し、直す作業は並行の別 WP にする。
3. **なぜこの問いが出てきたか**: 本 WP の手元アリーナ（40 ペア）で void が 1 ペア出た（2.5%・CLAUDE.md の 2% を超える）。原因を追うと
   符号化ではなくエンジンの順序の欠陥だった（両席 v15 で再現・両席 v14 では入らない）。効果による登場に制限を見させる直しを試したが止まらず、
   本体が順序だと分かったところで止めた（golden を動かす変更は本 WP の範囲外）。
4. **推薦**: (c)。v15 の符号化はこの欠陥と独立で、確認（世界に依らないこと・手の一致率・ゲート）は済んでいる。順序の欠陥は 2 枚が互いを出し合う
   カードの組で無限の往復になり得る＝ゲームプレイの正しさの欠陥なので、別 WP で golden の作り直しとレビューまで含めて直すのがよい。
5. **決めないとどうなるか**: OP17 のブロギー／ドリーが同じデッキに入る盤面で、まれに局が決着しない（アリーナでは void・生成では捨てられる）。
   アリーナの void 率がこの組の出やすい対面で 2% を超えると、判定が出せない測定が出る。
6. **留保**: 「親の効果を解決し切ってから誘発を消化」は他のカードの順序にも効く＝golden 監査の差分が広く出る可能性がある。
   今回の 40 ペアの勝率（0.449）は void を除いた参考値で、v15 の強さの判定には使えない（本番の判定はコーディネータのアリーナ）。
