# J-1: 打ち方の偏り（負けた側が使う型）の棚卸し(2026-09-25)

`price_realised.py`(T41・今の既定＝D-6採用後)の型別出力に、既存の行ごとの `price`／`real`
(`collect()` が既に計算済み・新しく計算していない)を最終的な勝敗(z)で再集計するだけの薄い
ラッパを通し、実300局（w41）・合成900局（w39+w42）で「型の使用率の偏り × 値段対実現の不整合」を
棚卸しした。診断のみ・新定数ゼロ・新しい価格計算ゼロ。T18 再開前の「全型の一括棚卸し」という
指示に対応する。

コーディネータ側で確認済み: 本報告が引く`by_family`の基準線(play 0.951/1.104・effect
0.464/0.196・attack 1.015/1.109)は`docs/reports/2026-09-25_d6_adoption.md`が確定した数字と
完全一致——今の既定(`decision_rows=main`・`cost_afford=check`)からの再計算であることを裏づける。

## 器と測り方

```bash
OPCG_LOG_SILENT=1 python tests/scripts/price_realised.py --in <w41>       --out pr_real.json
OPCG_LOG_SILENT=1 python tests/scripts/price_realised.py --in <w39> <w42> --out pr_synth.json
OPCG_LOG_SILENT=1 python winner_loser_tally.py <w41>       wl_real.json   # scratch・新しい価格計算はゼロ
OPCG_LOG_SILENT=1 python winner_loser_tally.py <w39> <w42> wl_synth.json
```

`price_realised.py` の型タグ(`move_family`・`primary_action`)と値段対実現の比(`ratio_real_over_price`)
・相関(`corr`)をそのまま使う。`winner_loser_tally.py`(scratch・リポジトリには置いていない)は
`price_realised.collect()` が返す `per[(seed, who)]["rows"]`(各行に既に `fam`／`act`／`price`／`real` が
入っている)を、その `rec["z"]`(1.0=最終的な勝者・0.0=敗者)で振り分けて数え直すだけ。**価格式・実現式は
1行も書いていない**。

両記録とも今の既定(`decision_rows=main`・`cost_afford=check`)の基準線と完全一致
(`by_family` の `ratio_real_over_price`: play 0.951／1.104・effect 0.464／0.196・attack 1.015／1.109
——`docs/cpu_theory_gap.md` D-6 の数字と同じ)ことを確認済み。

## 判定

- **実記録: 集中**——`play`の`?`バケット(D-6既知の登場時除去5種が主体)と`effect`の`RAMP_DON`
  (D-1既知)の2型で大半を占める。**新しい交絡は見つからなかった**。
- **合成記録: 分散・大半がノイズ**——単一の支配的な型は無く、上位はゼロ近傍の比が発散した見かけの不整合。
- **行数最大の2族(attack・attach)は使用率が対称**——打ち方の偏りという交絡が入り込む余地はそもそも薄い。

## 線形の橋の傾きギャップ(実0.296／合成0.353)にどれだけ効くか

**厳密な定量化はできなかった**——`theory_bridge.py`(cpu_theory_gapの0.296／0.353を出す本体の帳簿)に
型・カードIDでの除外切替が無く、D-1が自分のAUC診断で行った迂回も、本タスクの制約(診断のみ・新しい計算を
しない)の中では本帳簿には行えない。

**境界**: 打ち方の偏りが集中する2型は実の全priced行の13%(合成9%)にしかすぎず、行数で圧倒的に大きい
`attack`(45%)・`attach`(23%)は使用率が対称でここに交絡は無い。**打ち方の偏りが説明できるのはギャップの
少数派**——大部分は別の要因(`attach`族の設計上の低い実現・T52の非線形な勝敗変換・T87の帳簿の実現方式など、
台帳の他項目)に残ると見るのが妥当。

**因果ではなく相関の会計である**——「使用が敗者側に偏る」と「使用が負けの原因」は別。機構
(劣勢だから使う反応的プレイか、席・デッキの持続的傾向か)は本診断のスコープ外で未確定。

## T18 再開時の使い方(申し送り)

1. **`play`の`?`バケットと`effect`の`RAMP_DON`の2型は、T18で理論を方策として使う実験の勝敗差に
   これらの型の交絡が乗っている可能性を念頭に置く**——理論方策がこの2型の使用頻度・タイミングを
   実際のCPUと変えるなら、勝率差の一部はこの交絡(打ち方の癖の再現/不再現)から来る可能性がある。
   T18の判定(プラセボ比較)はこの交絡を自動的に相対化するので、既存の判定枠組みは壊れないが、
   型別のログ(`shadow_forbid`と同種の計器)でこの2型だけ個別に見る価値はある。
2. **`attack`・`attach`の2族は打ち方の偏りの外**——T18で観測される勝率差にこの2族由来の交絡は
   乗りにくい(使用率が対称なため)。理論方策の改善余地を探すなら、この2族の値段そのものの精度
   (既にほぼ良好)より、`play`/`effect`族の残る不整合の方が交絡の少ない対象。
3. **合成記録で交絡の再現性を毎回チェックする**——`RAMP_DON`のように実記録固有の交絡は、合成での
   汎化検証(`synth_roles`)ではほぼ消える。T18の判定を合成でも行う場合、実記録だけで見えた交絡が
   合成で消えているかを見れば「理論の欠陥」と「実デッキの打ち方の癖」を切り分けられる。
4. **本診断のスクリプト(`winner_loser_tally.py`)はscratchのみ・リポジトリ未収録**——再現したい
   場合は `price_realised.collect()` の戻り値を z で振り分けるだけの数十行なので、必要なら台帳の
   本文に埋め込むか、`tests/scripts/` に正式な計器として起こす判断はコーディネータ側で。

## 推薦

診断のみで完結させ、コードは変更しない。T18を再開する際は、本診断で洗い出した2つの既知交絡
(`play`の`?`バケット・`effect`の`RAMP_DON`)を型別ログで個別に監視し、合成記録でも同じ交絡が再現するかを
毎回チェックすることを勧める。線形の橋の傾きギャップ(0.296/0.353)を打ち方の偏りだけで大きく縮められる
見込みは薄い(交絡が集中する型は全priced行の9-13%にすぎず、行数最大のattack/attach2族は使用率が対称)。
T18の判定枠組み(理論方策 対 プラセボの比較)自体は本診断の結果によって変える必要はない。
