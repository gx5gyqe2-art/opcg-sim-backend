# NRel 学習の切り出し・予算を torch 側へ（2026-09-07・WP `train-torch2`）

`docs/rust_engine_plan.md` §18.6。§8.21（torch 化）で numpy のまま残っていた部分——バッチの
切り出し・`budget_feats`・R のゼロ配列の確保——を torch 側に寄せ、1 エポックをさらに縮めた。

## 結論（先に）

**指示書の見立ては外れていた。** 「ステップだけの見込み（7〜8 倍）に届かない差は Python の
バッチ切り出し・`budget_feats`・R のゼロ配列の確保」と書かれていたが、実測するとこの 3 つは
**1 エポックの 2.9%（0.70 秒 / 24.1 秒）しかない**。残りの 97% は torch の forward/backward の
中にある。

指示の 2〜5 はすべて入れた（numpy 側 0.70 → 0.23 秒）。そのうえで、**内訳が示した本当に重い所**
——forward が毎ステップ確保する番兵テンソル（`torch.full_like(x, -1e9)`）と、読まれない
マスク乗算——を**式を 1 ビットも変えずに**削り、value ステップを 1.34 倍にした。

| | 実測 |
|---|---|
| 1 エポックの学習ループ（4 コア・中央値 n=3） | **24.12 s → 20.28 s（1.19 倍）** |
| うち numpy に残っていた処理（指示の 2〜4） | 0.70 s → **0.23 s** |
| うち torch の forward/backward | 23.69 s → 19.76 s（value 1.34 倍・policy 1.05 倍） |
| holdout 評価（`train_sec` の外・指示の 5） | 2.65 s → **0.95 s（2.8 倍）** |
| a. loss 軌跡（**1 スレッド・895 ステップ**） | **ビット一致**（max abs **0.0**） |
| a. loss 軌跡（4 スレッド） | 0.435（**下限 1.123 より小さい**・下記） |
| b. budget のビット一致 | 全 **643,652 候補行**で max abs **0.0** |
| c. 目標 20 s | 今日のマシンの絶対秒では達成（20.28 s）。**§8.21 と同じ土俵に直すと 26 s 相当で未達**（下記） |
| numpy 経路 | `--backend numpy` で 1 エポック回る。holdout 指標は変更前と**ビット一致** |

## 2. 何を直したか

### 2-1. 予算は読み込み直後に 1 回だけ作る（指示の 2）

予算 3 は「方策点の盤面」と「候補行」と `ptab_ret` だけで決まる要素ごとの式なので、ステップの
たびに作り直す理由が無い。`budget_feats_all` が全 643,652 行ぶんを **0.2〜0.5 秒**で作り
`C["budget"]` に持つ。**実装は既存の `budget_feats` を点のかたまりごとに呼ぶだけ**＝式の正本は
1 つのままで、ビット一致は構造的に保証される（実測でも全行一致）。numpy 経路でも同じ配列を
切り出す（`budget_p` が 0.12 → 0.02 秒）。

常駐は候補行あたり 12 バイト増える（1 シャードで 7.7MB・16 シャードで約 120MB）。

### 2-2. 1 エポック分の index を先に作る（指示の 3）

`EpochBatches` がエポックの先頭で 1 回だけ:

- 候補行 index を `ragged_index`（`cumsum` 1 回）で作る＝ステップごとの
  `np.concatenate([np.arange(...) for i in bi])`（895 ステップ×64 点＝約 4 万回の `arange`）が消える。
- `seg` を「バッチ内の局所番号」で先に作る（`np.repeat(np.arange(n) % bs_p, lens)`）。
- 候補まわり（`at`/`cid`/`tcid`/`si`/`ti`/`pi`/予算／候補素性の末尾 4 列）をエポックの並びで
  1 回だけ集める。ステップでは**連続区間を切るだけ**（`narrow`＋必要なら dtype を上げる）。

`V` の各配列は**複製せず** torch に載せて `index_select`。**`torch.from_numpy` が受けない配列
（memmap＝read-only・非連続）は numpy の fancy index に落ちる**ので、§18.5 で `V` が
float16/int16 の memmap になっても同じ経路が動く（`V["tok"][bi]` の切り出しの形は変えていない）。

候補素性 139 のうち「action の onehot 7」と「末尾 4」は候補行だけで決まるので、末尾 4 は
`cand_tail_all`（**`NRelNet.cand_feats` に 0 の表を渡して取り出す**＝式の重複なし）で先に作り、
onehot は torch 側で `scatter_` で組む。学習対象の 128 列（主体/対象のカード表現）だけを
毎ステップ表から引く。

### 2-3. R は作らない（指示の 4）

`--ablate rel` のとき `None` を渡し、`TorchNRel` が**バッチ幅ごとに 1 本だけ持つゼロ**を読む。
従来は numpy でゼロを確保（1.8MB）→ torch へ複製 → forward の入口でもう一度 `zeros_like`
していた。値は常に 0 なので使い回してもビット一致する。

### 2-4. holdout も torch（指示の 5）

value の forward も方策 logits も `EpochBatches` 経由で torch で回す（2.65 → 0.95 秒）。
**指標（`seg_softmax`・top1・CE・v_mse・v_sign）の式は `n_rel_train` 側の 1 か所のまま**で、
差し替えたのは logits の計算だけ。

> 副作用: holdout の `pi_top1` が 1 スレッドで 0.4875 → 0.48775 に動いた。4,000 点のうち 1 点で
> argmax が入れ替わっただけ（logits の丸めが numpy と torch で違う）。`v_mse` は 16 桁まで
> 一致（0.7512661218643188）・`p_loss` の差は 4e-9（相対）。

### 2-5. ついでに: forward の一時テンソル（指示外・内訳が示した所）

内訳 1b が示したとおり `where`＋`fill_` が 1 割強を占めていた。**値も勾配も変えずに**削れる形が
2 つあった:

- `torch.where(m > 0, x, torch.full_like(x, -1e9))` → `torch.where(m > 0, x, -1e9)`。
  番兵をスカラで渡すと `[B,16,16,32]`（8.4MB）の一時テンソルの確保と読み出しが消える。
  −1e9 は float32 で厳密に表せる（15,625,000 × 64）ので値は同一。5 か所。
- 自×自の `c = c * mask_oo` を外した。`c` を読むのは直後の `where`（`mask>0` の枠だけ）で、
  そこでは `mask == 1.0` ＝ `c * 1.0` は `c` とビット一致し、`mask == 0` の枠は番兵に置き
  換わって値も勾配も 0 になる（`where` の backward が 0 を返す）。8.4MB の一時テンソル 1 本と
  その backward の掛け算が消える。

これで value ステップが 1.34 倍（13.51 → 10.08 秒）。**ビット一致は実測で確かめた**（受け入れ a）。

## 3. 受け入れ

### a. loss の軌跡（`tests/scripts/n_rel_torch2_check.py traj`）

**分岐元の `n_rel_torch.py` を別 module として import**（`--ref`）し、同じ seed・同じバッチ順・
同じ初期重みで 1 エポック（895 ステップ）を 2 本走らせ、**各ステップの loss** を比べた。

| スレッド | 比べたもの | loss 軌跡の最大絶対差 | 平均 | |
|---|---|---|---|---|
| **1** | 新経路 対 §8.21 | **0.0（ビット一致）** | 0.0 | ○ |
| 4 | 新経路 対 §8.21 | 0.435 | 0.0145 | 下記 |
| 4 | **§8.21 対 §8.21**（同じコードを 2 回） | **1.123** | 0.0329 | **下限** |

**1 スレッドでは 895 ステップすべてビット一致する**＝式も加算順も同じことの証明（最終 loss も
0.5138989090919495 で一致）。

**4 スレッドでは、§8.21 のコードを 2 回走らせても軌跡が再現しない。** 原因は torch CPU の
`index_select` の backward（`index_add_`）で、`tab` に 3 か所（トークンの `tab[ci]`・候補の
`tab[cid]`／`tab[tcid]`）から勾配が集まる方策ステップでは、スレッド並列の加算順が毎回変わって
`Wa`/`ba` の勾配が 1 ULP（相対 2e-7）揺れる。1 エポック回すとそれが軌跡の混沌で増幅される
（§8.21 の報告 c が「乱数初期値から 895 ステップの軌跡は丸めに対して混沌」と実測したのと
同じ現象）。**新旧の差（0.435）は、この下限（1.123）より小さい。**

> 指示書の基準「各ステップの loss が 1e-5」は、**4 スレッドではどんな実装でも達成できない**
> （§8.21 のコード自身が自分と一致しない）。**1 スレッドのビット一致**を式の同一性の証明とし、
> 4 スレッドは下限との比で読む——§18.4 の受け入れ b が「相対 1e-4（|g|>1e-6）は float32 の
> 丸めの下限より下にあるので下限との比で見る」と読み替えたのと同じ形。

### b. budget のビット一致（`n_rel_torch2_check.py budget`）

全 46,325 方策点＝**643,652 候補行**で、`budget_feats_all` の結果と従来の
`budget_feats`（バッチごと）が **`np.array_equal` で一致**（max abs 0.0・不一致バッチ 0）。
先に作る時間は 0.22 秒。

| | before | after | |
|---|---|---|---|
| 学習ループ `train_sec`（4 コア・中央値 n=3） | 24.12 s | **20.28 s** | 1.19 倍 |
| 同（1 スレッド） | 51.03 s | 43.93 s | 1.16 倍 |
| 1 エポック全体（読み込み・評価込み） | 35 s | **29 s** | |
| （参考）§8.21 の同条件・別マシン状態 | 34.7 s | — | 同じコードが今日 24.1 s |

**目標 20 秒は「§8.21 と同じ土俵」では未達。** 今日のマシンで換算すると
34.7 × (20.28 / 24.12) = **29.2 秒相当**。届かない分がどこに残っているかは §1 の内訳のとおりで、
**numpy 側はもう 0.23 秒（1.1%）しか残っていない**——残る 19.8 秒は torch の forward/backward
そのもの（うち行列積が 3 割弱）。ここを削るには式（対の全ペア展開）か加算順を変えるしかなく、
それは受け入れ a（軌跡の一致）と両立しない。次の手は §5 に書く。

### numpy 経路が壊れていないこと

`--backend numpy` で 1 エポック回る（115.95 s → 119.66 s＝振れ幅の内側）。**holdout 指標は
変更前と 16 桁まで一致**（`val_vmse` 0.7411069869995117・`val_p_loss` 1.8416580276489258・
`val_pi_top1` 0.4925）＝参照実装（手書き backward）の経路は値が 1 ビットも動いていない。

## 4. 実装のかたち

- `opcg_sim/learned/train/n_rel_train.py`
  - `Split`（区間計測・常時オン）と `N_REL_TRAIN_EPOCH` の `breakdown`。
  - `budget_feats_all`（`budget_feats` をかたまりごとに呼ぶ）・`cand_tail_all`
    （`cand_feats` に 0 の表を渡して末尾 4 列を取り出す）。どちらも**式の正本を増やさない**。
  - `eval_policy` は `src`（`EpochBatches`）があれば logits だけ torch で回す。指標の式は共通。
- `opcg_sim/learned/train/n_rel_torch.py`
  - `ragged_index`・`_Rows`（torch に載れば `index_select`／載らなければ numpy の fancy index）・
    `EpochBatches`（エポック先頭で 1 回・ステップでは連続区間を切るだけ）。
  - `PolicyBatch`（盤面以外の候補まわりを 1 つにまとめた袋）と
    `policy_batch_from_numpy`（従来の呼び口・テストと照合 CLI 用）。
  - `TorchTrainer.policy_step`（従来の引数・袋を毎回組み立てる）と `policy_step_b`（袋を受け取る）。
  - `TorchNRel.rel_zeros`（バッチ幅ごとの使い回し）・番兵のスカラ化。
- **`load_dump_v2` と `V`/`P`/`C` の形は触っていない**（§18.5 と並行するため）。`C` に足したのは
  指示 2 が指定した `C["budget"]` だけで、`load_dump_v2` の中では作らない（訓練器が作る）。

## 5. 残るもの（次の手・未実施）

1 エポックの残り 19.8 秒は forward/backward。**式を変えれば大きく減る余地がある**——例えば
自×自の `cat([t_i, t_k, R]) @ Wc` は `t@Wc[:48]` と `t@Wc[48:96]` を broadcast で足す形に
書き換えれば `[B,16,16,101]`（26MB）の組み立てが要らなくなる（`cat` 7.7%＋`mm` の一部）。
ただし**加算順が変わる**ので、本 WP の受け入れ a（軌跡の一致）は満たせない。やるなら
「holdout 指標が相対 1e-2 以内」（§18.4 の受け入れ c と同じ土俵）に基準を移した別 WP にする。

`index_add_` の非決定性は `torch.use_deterministic_algorithms(True)` では解けない
（`index_add_` に決定的な実装が無く例外になる）。**1 スレッドなら決定的**なので、軌跡の再現が
要る照合は 1 スレッドで行う。
