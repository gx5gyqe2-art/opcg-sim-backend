# T85——ドン付与の増分が**帳簿で二重に数えられていた**（付与の行 ＋ 殴る行の増強済みパワー）。記録で確かめて**移転を 1 回だけ**数えるようにしたが、**これは「帳簿が 2 倍」の原因ではなかった**（`g` の実効値は 1.1% しか縮まず必要な `κ` は 0.502 → 0.509）。**外れた予告が次を指した——膨らみの主犯は守り側**（攻撃だけなら必要な `κ` 1.052／1.122 が、攻め＋守りで 0.637／0.665 に落ちる）

2026-09-18 実施（ユーザ指示「進めてください」＝T84 §4 の 2）。**当てはめない・新定数ゼロ**（規約を揃えるだけ）。
本報告は特定時点のスナップショット。器は `theory_bridge.ATTACH_LEDGER_MODE`（`increment` 既定／`in_attack`）・
`--attach-ledger`・`stats.attach_ledger`／`attach_zeroed`。

## 1. 問い

T81〜T84 で型別に割った相関のうち、**付与（ドン）は 0.064／0.033** で、ほとんど情報を運んでいなかった。
一方で**全体の必要な `κ` は 0.50** なのに**攻撃だけなら 1.05／1.12**＝**全体の帳簿はおよそ 2 倍に膨らんでいる**。
「膨らみ」の候補として最も筋が通るのは**同じ移転を 2 回数えること**なので、そこを記録で確かめた。

## 2. 記録で確かめたこと（実デッキ 8 ファイル・読み取りだけ）

エンジンでは**攻撃は全部 `DON_BOX`（対象付き）の形**で来る（`search/decide.rs::don_box_first_primitive`＝
「ドンを k 枚付けてから殴る」マクロ手）。価格の元になる `slot_power` は**自席のターンには付与ドンを載せたパワー**
（`price_realised` の 2026-09-16 の訂正と同じ事実）。

```
攻撃の行 2,071
  うち **既に付与ドンが乗った体で殴っている行 521（25%）**
      他の増強が混ざらない行での内訳:
        パワー = 印字 + 1000k（＝増分が攻撃の価格に入っている） **102**
        パワー = 印字のまま（＝入っていない）                      **3**
純粋な付与の行（対象なし） 975
```

＝**付与の行で `attach_value`（増分）を計上し、その体が殴る行でも増強済みのパワーで計上している**＝
**同じ +1000k を 2 回**。T62（守りの窓）で直したのと同じ型の誤りで、**零和の帳簿では同じ移転は 1 回**数える。

## 3. 式（新定数ゼロ）

```
ATTACH_LEDGER_MODE = in_attack   純粋な付与の行の帳簿価格 g を 0 にする
                                 （増分は「その体が殴る行」の価格に入っている＝払われた所で 1 回）
決める価格 s                     増分のまま（T58 の分離: 決めるのは option・数えるのは exercise）
```

**体が殴らずにターンが終われば**（付与ドンはターン終了で戻る）**損害は実現していない**＝0 が正しい。

## 4. 予告した検算（測る前に書いた）

1. **付与の型は帳簿から消える**（`g = 0` になるので `|g| < 0.005` の床で落ちる）。
2. **全体の必要な `κ` が 0.50 から上がる**（重複が減るぶん帳簿が縮む）。**0.6 前後**を予測。
3. **攻撃の型の `κ` は 1.05／1.12 のまま**（触っていない）。
4. **`ΔG` は変わる**（行から価格が消えるため）＝帯と傾きは測り直す。傾きは 1 に向かって上がると予測。

## 7. 読み方

- **上手くいった: 誤りは実在し、規則と零和の規約どおりに直せた**。記録で「攻撃の価格に増分が入っている」ことを
  確かめたうえで、付与の行を 0 にした。**接戦帯と中盤帯は両記録で上がり、傾きも下がらない**。
- **上手くいかなかった（そして重要）: これは「帳簿が 2 倍に膨らんでいる」原因ではなかった**。
  **付与の価格は小さすぎる**——`g` の実効値は 1.1% しか縮まない（`c(x)` の段が平らな区間では増分が 0 になるため）。
  **予告 2 が外れたことが、次にどこを見るべきかを教えている**。
- **膨らみの主犯は守り側**（本 T の副産物として読める）: **攻撃だけなら必要な `κ` は 1.05／1.12** なのに、
  **攻め＋守りにすると 0.637／0.665** に落ちる＝**守りの `g` を足すと帳簿の大きさは増えるが、勝率の動きと揃っていない**。
  さらに出す手・効果を足すと 0.509／0.508。**つまり「2 倍」の半分以上は守りの側**。
  T28-b／T28-c で「守りの規則は逆を向いている（暫定）」と出ていたのと同じ場所で、
  **今回は「大きさが倍」という形で出た**（符号ではなく倍率）。
- **プール AUC と決着帯が下がったのは、決着帯で付与の価格が「勝っている側の手数」を数えていたため**と読める
  （罠 30 系＝勝敗の言い換え）。T80 の規約どおり**プール AUC は看板にしない**ので、採否は接戦帯・中盤帯・傾きで読む。

## 8. 次（ユーザ判定）

1. **既定を `in_attack` にするか**（本報告の判定事項）。推す理由は**正しさ**（同じ移転を 2 回数えない・記録で確認済み）で、
   数字の得は小さい（接戦 +0.003／+0.002・中盤 +0.004／+0.003・傾き +0.002／+0.021）。費用はプール AUC −0.02 と決着帯 −0.017／−0.007。

   守りの窓の `g`（T62 の `delta`＝攻め手の価格 − 実際に払った額）が**同じ移転を攻め手の行と二重に数えていないか**を、
   本 T と同じやり方（記録で確かめる）で見る。**P8 待ちではない**——二重計上の確認は記録の現状でできる。
3. 速さ `A`（残り 3）。4. 効果の型別と `κ` の形。
