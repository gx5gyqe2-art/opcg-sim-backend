## 1. 計測の設計と予告（数を見る前に固定）

### 1.1 内訳の計測

**対局**: serve 既定の両席（出荷既定 r11a・sims 160・worlds 4 ほか serve 既定のまま）で 20 局。`synth_roles`・`random` 対面・1 プロセス。

**計時**:
- Rust に計時を入れる（`OPCG_PROF=1` のときだけ動く・既定は切＝1 bit も変わらない）。
- 区間は**排他**で数える。区間の中で別の区間に入ったら、内側の時間は内側の区分にだけ数え、外側には数えない。
- 世界ごとのスレッドの時間は足し合わせる＝CPU 時間。`decide` 1 回の壁時計は別に数える。

**区分**:

| 区分 | 中身 |
|---|---|
| ネットの forward | `net::value`・`net::priors`（トークン・本体・方策の頭） |
| 符号化 | 盤面 → ネットの入力（`encode`） |
| 候補の素性 | 方策の候補行の組み立て（`cand_rows` と候補の識別） |
| 合法手の生成 | `legal_actions`（準備箱の候補の列挙を含む・箱の中で呼ぶ評価は内側の区分へ） |
| 手の適用と巻き戻し | `apply_move_inplace`・transaction の巻き戻し |
| 世界の引き直し | `determinize`（局面の複製を含む） |
| 探索のその他 | 上のどれでもない Rust 側（木の操作・PUCT・束ね） |
| Python 側 | PyO3 の往復・opts の JSON・出力の JSON（`py_game.decide` の壁時計から Rust の `decide` の壁時計を引く）と、`driver` の Python の処理 |

- 「PIMC の世界の数だけの繰り返し」は、区分ではなく倍率として書く。世界 4 本は今もスレッドで並列に回っている
  （`run_worlds`）。そのため CPU 時間は世界の数に比例し、壁時計は 1 本ぶん＋同期になる。
- 1 局の手数（`decide` の回数）と、1 手の秒の平均・分布（窓／main 別）も出す。

### 1.2 高速化の方針

- **結果を 1 ビットも変えない高速化だけを採る**。同じ seed で同じ手・同じ訪問数になること。
  golden 2 本（監査 3,386 件・再生 200 局）と `make test`・`make audit-cross`（void 0）がそのまま通ること。
- 内訳の大きい順に当たる。候補:
  - **同じ盤面の forward の使い回し**: 木の展開で `priors`（符号化＋トークン＋本体＋方策の頭）を回した直後に、
    窓を解決しない葉では同じ盤面・同じ席で `value`（符号化＋トークン＋本体＋価値の頭）をもう一度回している。
    本体までを 1 回にすれば、同じ演算を同じ順で 1 回だけ行う＝ビット一致。
  - 割り当ての削減（`affine` の出力ベクトル・候補行の `Vec`・`legal` の複製）。
  - forward の行列計算の並べ方（加算の順を変えない範囲で）。
  - 局面の複製の軽量化。
- **結果が変わる案は測るだけで採らない**（探索の回数・世界の数を減らす・ネットの量子化・加算順を変える SIMD など）。
  採るならアリーナが要る＝ユーザ判断。

### 1.3 予告（司令塔の予告をそのまま固定）

- **内訳の最大はネットの forward（CPU 時間の 5〜7 割）**。
- **ビット一致の高速化で 1 局 1.5〜2 倍**。
- 補足の読み【推測】: 上の「使い回し」が効く葉は、展開のたびに 1 回ある。forward の 3〜4 割が二重計算なら、それだけで forward は 0.6〜0.7 倍になる。
