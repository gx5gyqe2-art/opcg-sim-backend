## 2. 追加で見つかった2欠陥（前報の3件に続く4件目・5件目）

### 2.1 自己参照コストが「別のカードで払える」に化ける（seed 904002）

`P-081 ジュラキュール・ミホーク`【起動メイン】「**この**キャラを持ち主の手札に戻すことができる：
自分の青の特徴《クロスギルド》を持つキャラが3枚以上いる場合、手札からコスト5の《クロスギルド》
キャラ1枚までを、登場させる」。

コストの自己参照が `ref_id='self'` に固定されず、汎用の対象解析へ落ちて
**zone=FIELD / player=ALL＝「場のキャラなら誰でもよい」**（相手のキャラでも可）に化けていた。
発生源は場に残るのでターン制限の無い起動メインを撃ち続けられ、効果で盤面が元に戻る
**3手周期の無限ループ**になる。1手5〜6秒かかるため、上限手数より先にペアの時間上限（900秒）に
当たっていた——「重い局面」に見えていたものの正体。

- パーサ: 動詞表 `_SELF_COST_VERBS`（レスト／トラッシュ／手札に戻す／デッキの下）で一括固定。
  「ドン!!コスト，このXを〜」の複合形も後段を `_parse_cost_node` へ通す。
  **DB 全体で該当 96節 → 0件**（テストでラチェット）。
- 判定側: `_can_satisfy_node` も `ref_id='self'` を候補列挙を経由せず発生源自身にする
  （経由するとステージの自己コストが「払えない」に化ける）。
- **ルール上の実害**: 挙動ベースラインの差分2行が示すとおり、`OP02-035 トラファルガー・ロー` と
  `P-074 ポートガス・D・エース` は**相手のキャラを手札に戻してコストを払っていた**。
  無限ループとは別に、対戦の正しさそのものが壊れていた。

検証: seed 904002 は 141手・12ターン・**126秒で正常決着**（修正前は同じ141手目でループ中）。

### 2.2 イベントが場に登場する（seed 907006）

`ST31-002 ジンベエ`「自分の手札からコスト1の特徴《麦わらの一味》を持つ**カード**1枚までを、
登場させる」は「キャラカード」と言わないため対象種別が無制限（`card_type=[]`）に解析され、
イベント `ST01-016 悪魔風脚` が場に登場していた。イベントは「発動」するもので「登場」はしない
＝ルール上あり得ない盤面。場に残ったイベントは【メイン】がコストなしの起動メインとして列挙され、
「1枚まで選ぶ」を選ばない空振りを **426回連続**で撃っていた。

候補側（`resolver._resolve_targets`: PLAY_CARD の候補はキャラ／ステージのみ）と
適用側（`per_target.play_card`: EVENT は場に置かない）の両方で塞いだ。

検証: seed 907006 は 900秒超過 → 14ターン159手 **67秒で正常決着**。

## 3. 5欠陥の並び（本件で確定した分類）

| # | 欠陥 | 発見 | 型 |
|---|---|---|---|
| 1 | ドン!!へのフリーズで対局が落ちる（OP10-033） | 交差対面監査 | 例外 |
| 2 | 再計算がコスト確認の対話を無限に出す（OP09-080） | 交差対面監査 | 上限手数 |
| 3 | 状態変更コストが「既にその状態」でも払える（OP15-099） | 交差対面監査 | 上限手数 |
| 4 | 自己参照コストが別カードで払える（P-081 ほか96節） | void 再生 | 時間上限 |
| 5 | イベントが場に登場する（ST31-002→ST01-016） | void 再生 | 時間上限 |

**1〜3 は「上限手数／例外」で出るのでミラー監査を交差対面へ広げれば掘れる。4〜5 は
「1手が遅いループ」なので手数では捕まらず、時間上限（void）としてしか現れない**——
つまり void を「測れなかった残骸」として放置すると、この2種は永久に見つからない。

## 4. 運用の固定（同じ穴を二度掘らないため）

### 4.1 交差対面監査を常設ゲート化（`TEST_SPEC` §5.0）

```bash
make audit-cross            # 既定120件・約10分・合格 = hang/timeout/error = 0
```

**エンジン/パーサを変更したときの push 前ゲート**とする（`CLAUDE.md` にも明記）。
`make test` に入れないのは、120件で約10分＝ゲートを倍にするうえ、掛ける価値があるのが
エンジン/パーサ変更時に限られるため。`CROSS` / `CROSS_SEED` で件数と対面集合を変えられる。

### 4.2 アリーナ昇格判定の要件（`TEST_SPEC` §5.05）

1. **条件を2本以上**（主＝ランダム対面×生成デッキ／副＝固定ミラー）。主で昇格基準
   （wr≥0.55 かつ CI下限>0.50）、副で非退行（CI下限≥0.45）。
2. **判定は測定時のコミットに紐づく**＝エンジンを触れば過去の昇格証拠は失効しうる。
3. **void 率が2%を超えたら判定を出さず原因を潰す**（今回の 5.4% は実バグ5件だった）。
4. **判定に使ったネットは不採用でも消さない**（gen16 は候補置き場に残っていたので再生できた）。
5. **台帳は消える前提**（作業台帳は gitignore・実行環境は巻き戻る）＝中間集計を逐次記録し、
   結果はレポートへ落とす。
