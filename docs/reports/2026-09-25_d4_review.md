# D-4 見直し: コスト判定の規則の誤りと、物差しの窓の早閉じ（2026-09-25）

ユーザ指示「一応見直してくれる？ 変わらずなら採用で」を受けて、D-4（`2026-09-25_d4_cost_afford_full.md`）の
結論を実測で検め直した。**変わった**——採用は保留し、以下を報告する。`2026-09-25_d2_don_cost_gate.md`・
`2026-09-25_d3_linear_bridge_don_gate.md`・D-4 報告の結論のうち、ここで訂正するものがある（報告自体は
スナップショットとして改変しない）。

## 1. D-4 報告の「ΔS の改善幅が狭い版より小さい原因」は誤りだった

D-4 報告は「自分自身が対象」の直しが相殺したと書いたが、**実測で分解していなかった**。部品を 1 つずつ
外す差し替え（計測専用・`off` と同じ入力で `check` の各部品だけを落とす）で実記録 300 局の線形の橋を
回した（検算: 全部入り＝0.6147／ドンだけ＝0.6217 を正確に再現）:

| 外した部品 | `ΔS` AUC／傾き |
|---|---|
| なし（全部入り） | 0.6147／0.1387 |
| 自分自身・リーダー・枚数・ライフ／トラッシュ・ドン起点の付与（それぞれ単独） | **0.6147／0.1387（1 桁も動かない）** |
| ドンをレストにするコスト（`REST_DON`） | **0.6217／0.1495（D-2 の数字に戻る）** |

差は全部 `REST_DON` の 1 部品から来ており、「自分自身」は寄与ゼロ。

## 2. ドン‼️コストの規則がエンジンと食い違っていた（D-2 から）

エンジン（`rust/opcg_engine/src/effects/resolver.rs::can_satisfy_node_on`・`rules/actions.rs` の PLAY）と
突き合わせた:

* **ドン‼️−N（`RETURN_DON`）**: エンジンは**場のドンの合計**（アクティブ＋レスト＋付与中）で判定する
  （レストのドンも戻せる）。D-2／D-4 はアクティブだけと比べていた＝**厳しすぎた**。
* **ドンをレストにするコスト**（`REST_DON`・自分のアクティブなドンを付ける `ATTACH_DON`）: エンジンは
  手札から出す札の**コストを先にアクティブなドンのレストで払ってから**登場時・【メイン】を解決する。
  D-4 は払う前のアクティブと比べていた＝**甘すぎた**。

直した（`check` の中だけ・`off` は不変）: ドン‼️−N は `st["my_don_total"]`（`price_realised.don_stock`＝
エンジンの合計と同じ量・`theory_bridge._state_of` が既に積む）と、レストにするコストは
`st["my_don_active"] − 札のコスト` と比べる。状態を渡して呼ぶ経路は全部「手札から出す」文脈で、
効果でただで出す相方（T70・`effect_value.py` の `free_value` 呼び出し）は状態を渡さないので来ない。
テストを追加（レストのドンでも戻せる・コストを払った後のアクティブで見る等）。

## 3. D-2 の「? バケットの符号が直った」は誤った規則の副産物だった

正しい規則で測り直すと、実記録の play の「?」バケット（D-1 の不整合）は**元の食い違いに戻る**:

| 実記録・play「?」（n=1432） | 価格 | 実現 | 比 |
|---|---|---|---|
| 旧（`off`） | +0.01076 | −0.01005 | −0.934 |
| D-2（アクティブだけ） | −0.00387 | −0.01005 | +2.597 |
| 正しい規則 | **+0.00720** | −0.01005 | **−1.395** |

線形の橋の `ΔS`（実）も、正しい規則では旧より**わずかに下がる**（0.6014→0.5954・傾き 0.1229→0.1133）。
合成はほぼ不動（0.4678→0.4694）。`ΔG` は両記録ともビット単位で不変のまま。D-2〜D-4 の `ΔS` の「改善」も
同じ副産物だった。

## 4. 本当の原因: 物差しの窓が「選択の問い」で閉じ、効果の解決前を読んでいる

OP15-074〜078 を選んだ実記録の 886 行を直接追った: リーダーは全部エネル（条件成立）・294 行はアクティブな
ドンもあったのに、次の判断点までに場のドンは **1 度も減っていない**。1 局を行ごとに見ると理由が分かる:

```
PLAY OP15-077                  レスト 3・合計 6
RESOLVE_EFFECT_SELECTION       レスト 3・合計 6   ← 「戻すドンを選べ」の問い（自分の kind 0 の行）
PLAY OP15-077                  レスト 2・合計 5   ← ここで初めてドンが戻り効果が解決している
```

エンジンはドン‼️−N を払うときに**どのドンを戻すかの問い**（`interact.rs::suspend_for_don_selection`・
飛ばせない）で中断し、その答えの行は**自分の kind 0 の行**として記録される。`price_realised.py` の
「次の自分の判断点」（T47 で kind 1/2 を外した）はこの問いの行を拾うので、**窓が効果の解決前で閉じ**、
実現は「札が手札から出た（−μ）」だけになる。**効果は実際には解決している**——D-1 が保留した
「エンジン側で発動していない別問題か」でもなく、値段の側の問題でもなく、**物差しの側の問題**だった。

範囲（次の判断点が選択の問いの行である窓の割合）:

| 型 | 実 | 合成 |
|---|---|---|
| play | **1816／4013（45.3%）** | 1586／8645（18.3%） |
| effect | 0／1348（0%） | 500／2847（17.6%） |
| attack | 1／7353 | 12／18195 |
| attach | 0 | 0 |

実記録の登場の窓の **45%** が効果の解決前に閉じている。D-1（型ごとの値段と実現の不整合）の
play・effect 族の数字は、この早閉じを含んだまま読んでいた。

## 読み

* **コストの支払い判定（正しい規則）は正しいが、今の物差しでは良し悪しを判定できない**——
  値段を実現に近づける直しの効果を測る物差しが、登場の半分近くで効果の解決前を読んでいるため。
* 次に直すべきは**物差し**（「次の自分の判断点」から選択の問いの行を外す＝T47 と同じ直しを kind 0 の
  問いの行にも当てる）。その上で D-1 を測り直し、コスト判定の採否もその物差しで判断する。
* 既定は `COST_AFFORD_MODE=off` のまま（採否はユーザ判断）。
